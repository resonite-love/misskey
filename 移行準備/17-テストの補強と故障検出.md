# テストの補強と故障検出

2026-11-12、Claude Code と実装時の会話を引き継がないエージェントによるテストレビューを受け、見逃しやすい条件を補強した。今回の変更はテストと記録であり、利用者向けの機能や API 仕様は変えていない。

## 補強した検査

| 対象 | 確認する内容 |
| --- | --- |
| 履歴と本文 | 時間指定で古い投稿が消え、新しい投稿は残る。履歴の `active` も確認する。制限しない時刻への変更と設定解除で古い投稿が戻る |
| 検索 | 相手サーバーが応答できていることと非表示を同時に確認する。設定解除後は同じ検索語で本文を取得できる。設定の適用・解除を相手側で確認してから検査する |
| SQL | 実装の `noteNewerThanPolicySql` と `filterNoteVisibility` を PostgreSQL で実行する。6種類の ID、境界の前後・一致、絶対時刻・経過時間・0・未設定、閲覧者と送信元／受信先の違いを確認する |
| LTL | ローカル投稿が残ることと相手側の投稿の表示条件を確認する。DB、DB へのフォールバック、Redis をそれぞれ通す。Redis の検査では `sinceId` を渡さず、DB へのフォールバックを無効にする |
| 投稿者の設定 | 相手側にフォロワーがいなくても3項目の設定と解除が届く。キャッシュ済み投稿の本文が隠れ、解除後は戻る。フォロワー向けの履歴では閲覧者の権限を区別する |
| 一時的な取得拒否と削除 | 取り込み済みの投稿を取得できなくなっても、同じキャッシュ行を保持し削除記録を作らない。復旧後は再取得でき、実際の削除ではキャッシュを消して削除記録を残す |
| 初回フォローコピー | フォロー解除・申請取消後に処理待ちの状態を再現する。実際のワーカーがロック待ちに入ったことを確認し、再試行してもフォローや申請を復活させない。待機中の旧側のフォロー変更は初回スナップショットに加えない |
| リアクション | 変更直後の API 応答、DB のリアクション、件数を確認してから取り消す |
| 投票 | 未投票の新しいアンケートに範囲外の選択肢を送る。拒否後の投票行・票数が増えないことと、その後の正しい投票が成功することを確認する |
| 応答形式 | `unavailable` を含む応答全体を照合し、削除・一時的な取得拒否・不正な空応答を区別する |

SQL の試験用テーブルは専用接続の一時テーブルとし、トランザクションをロールバックして破棄する。LTL 用の投稿は fanout を有効にしてから作成し、試験後に元のサーバー設定へ戻す。

## 意図的な不具合による確認

テストが通るだけでは、必要な不具合を検出できるとは限らない。正常な実装での成功を確認した後、下表の不具合を一つずつ入れて失敗箇所を調べた。

| 入れた不具合 | 検出する検査 |
| --- | --- |
| 時間制限の SQL を常に真にする | 時間条件と閲覧者の SQL 試験 |
| 境界の比較を `>` から `>=` にする | 境界時刻と一致する投稿の SQL 試験 |
| 応答の `unavailable` を捨てる | 応答全体の照合 |
| 投票先の範囲確認を外す | 未投票のアンケートへの不正な投票 |
| 既存リアクションの変更だけ無視する | 変更直後のリアクション照合 |
| 初回コピーで利用者の取消記録を無視する | 再試行後の取消状態・フォロー・申請の照合 |
| 時間制限がある投稿者の履歴をすべて空にする | 新しい投稿が履歴に残ることの確認 |
| 制限対象の検索で、相手の障害を表す空応答を返す | `peerAvailable` の確認 |
| 匿名のローカル限定表示で、DB の候補をすべて落とす | LTL にローカル投稿が残ることの確認 |

単体試験の不具合は作業用コピーに入れた。実 API 試験の不具合は専用の G/R テストサーバーのビルド済みファイルにだけ入れ、各試験の後に元のバイト列へ戻して再起動する手順を使った。ソースコードに不具合は残さない。

| --- | --- |
| 故障検出 | PASS。上記9種類をそれぞれ検出した。うち SQL の制限無視・境界比較・`unavailable` の欠落は、補強前の試験では見逃していた |
| 通常の単体試験 | PASS。両フォークとも29件。実装の SQL、投稿応答、投稿者の設定を検査 |
| 通常の実 API 試験 | PASS。正常な実装へ戻した後、`test-public-visibility.mjs` の36項目、`test-search.mjs`、`test-actions.mjs`、`test-link.mjs` を再実行 |
| 初期設定が異なる場合 | PASS。両側で fanout を無効にしてから公開範囲の試験を開始し、Redis の検査成功と元の設定への復帰を確認 |
| backend の型検査 | PASS。両フォークで確認 |
| 独立した再レビュー | PASS。設定変更の反映待ち、Redis 用データの作成条件、非表示本文の照合を修正し、再確認で残る具体的指摘なし |
| API 型生成・migration・frontend | SKIPPED。API 定義・DB スキーマ・画面の変更なし |

故障を入れた6回の実 API 試験では、対象のビルド済みファイルが元の SHA-256 と一致することを確認した。試験用の変更はテストサーバーから除去済みである。

作業環境の `../gridspace-test-review-20261112/experiments/` に、単体試験の `strengthened-unit/results.json`、実 API 試験の `runtime-mutations/results.json`、各試験のログを保存した。`final-test-*.log` が正常な実装へ戻した後の結果である。元のテスト監査と今回の故障検出を区別できるよう、補強前のログも残している。認証情報やアカウント情報はコミットしない。

## 検証の限界

初回コピーの試験は、処理完了の保存前に停止した場合の処理待ち状態を DB で再現している。ワーカーの実行中にプロセスを落とす試験や、同じ瞬間に利用者が取消操作をする試験ではない。SQL の閲覧者別試験も、すべてのメンション・返信・非公開投稿の組み合わせを網羅してはいない。

今回の補強は、総合レビューで残った実装上の指摘をすべて修正したことを意味しない。機能側の残件は [16-レビュー指摘と公開範囲の修正](16-レビュー指摘と公開範囲の修正.md) を参照する。
