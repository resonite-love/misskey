# 絵文字の双方向同期

2026-11-18の合意: 両サーバーで追加・変更した絵文字を同期する。削除と同名の衝突は自動反映しない。

リリース: れぞらぶ `2026.11.0-resonite-love.31.62`、ぐりすぺ `2026.11.0-grid-space.31.63`。

同期は設定済みのサーバー間に限定する。ぐりすぺ側を調整役とし、両方の絵文字IDと前回同期時の内容を保存する。変更を受け取った側から同じ変更を送り返すループを防ぐ。サーバー間通信は既存の署名と再送防止を使う。

同期するのは名前・画像・カテゴリ・別名・ライセンス・センシティブ設定・ローカル限定設定。ロールIDはサーバーごとに異なるため、ロール制限のある絵文字は自動反映せず管理者確認にする。画像は通常のドライブ取り込み処理を使って保存する。

同期済みの片側だけが変わった場合に反映する。両側の変更、同名で内容が違う既存絵文字、削除、名前の衝突は管理画面で確認する。反映直前に相手の内容を再確認し、確認後に編集されたものを上書きしない。管理者は片側の内容を採用するか、その組を同期対象から外せる。削除の伝播は実装せず、通常の絵文字管理画面で行う。

初期確認ではれぞらぶ2,553個、ぐりすぺ2,535個。れぞらぶだけ51個、ぐりすぺだけ33個、共通名の設定差分4個だった。この数は画像の一致までは検証していない。以前の一括取り込みで取得できなかった画像48個は、今回も自動的に取得できるとは限らない。

変更の確認はバックグラウンドで行い、変更のない画像は取得しない。失敗は間隔を空けて再試行し、再起動後も同期状態を引き継ぐ。

検証: バックエンド41件、フロントエンド4件、ローカルの2つのPostgreSQLを使った統合チェック16項目が成功。統合チェックには双方向の追加・更新、同じ設定の往復変更、応答喪失後の復旧、同時編集、削除後の再作成、画像の取得中の変更、処理の偏り、別プロセスからの状態参照を含む。新規migrationのup/downとエンティティの一致も確認した。APIとVueはそれぞれ独立したエージェントがレビューした。

lint・SPDX・locale safetyとフロントエンドのビルドは成功。バックエンド全体の型検査は既存の `WebhookTestService.ts` の `noRelay` 型で失敗し、今回の変更ファイルには型エラーがない。通常の `pnpm --filter backend check-migrations` は作業ツリーのnode_modulesがジャンクションのためpnpmに拒否されたので、同じ検査スクリプトを直接実行し、pending DDLがないことを確認した。

本番反映前の再確認では、同名の2,502組のうち2,498組は画像と設定が一致し、4組は設定が異なった。両サーバーともローカル絵文字名の重複はなかった。画像の取得先を持つドライブレコードが見つからない絵文字は、れぞらぶ側に47個あった。

CHANGELOG候補: れぞらぶとぐりすぺの絵文字を双方向に同期し、確認待ちや失敗を管理画面で扱えるようにした。

無変更時にJSONBのキー順だけで更新が発生しないよう、状態の比較は固定順のハッシュと処理状態に限定した。統合テストで連続した無変更の同期後も各行の更新日時が変わらないことを確認した。`.31.61` / `.31.62` の最初のビルドは本番へ出さず、この修正版を使う。
