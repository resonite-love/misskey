## 残る問題と対応順

「コード確認」は問題に関係する処理が現在も残ることを読んで確認した状態。「要再現」は総合レビューの指摘または仮説で、今回確認したコミットに対する実通信・競合試験ではまだ確定していない状態を表す。以下の優先順は本番前の作業を決めるための提案である。

### 優先1: 利用者の操作・権限に関わる問題

| ID | 問題と影響 | 確認状況・次の作業 |
| --- | --- | --- |
| R01 | フォロー処理がロック用の接続を保持したまま相手と通信する。専用プールは2接続で、相手の遅延時に無関係な解除・ブロックまで待たせるおそれがある | **コード確認、負荷時は要再現。** [FollowGuard](../packages/backend/src/core/gridspace/GridspaceFollowGuardService.ts)、[FollowExpansion](../packages/backend/src/core/gridspace/GridspaceFollowExpansionService.ts)、[LinkService](../packages/backend/src/core/gridspace/GridspaceLinkService.ts)。通信をロックの外へ出し、待ち時間を制限する。複数プロセスと遅延した相手で、通常操作が完了することを試験する |
| R02 | 旧名義返信 API に `secure: true` がなく、専用権限を持つ第三者アプリのトークンからも呼べる。添付は旧側の所有ファイルかを確認するが、連携経由でアップロードしたものだけには制限していない | **コード確認、API の再現試験が必要。** [private-reply](../packages/backend/src/server/api/endpoints/gridspace/private-reply.ts)、[ReplyService](../packages/backend/src/core/gridspace/GridspaceReplyService.ts)。文書13の「操作はログインセッション限定」と揃える。旧ドライブの別の添付を再公開できる範囲も検査する |
| R03 | 外部から届くフォロー却下では、利用者の取消を保存する処理を通らない。コピーの再試行で再申請するおそれがある。また、自動フォロー中のブロックと申請作成の競合が未検証 | **却下経路はコード確認、競合は要再現。** [UserFollowingService](../packages/backend/src/core/UserFollowingService.ts)、[UserBlockingService](../packages/backend/src/core/UserBlockingService.ts)。remote Reject とブロックの発生順を変え、申請を復活させないことを確かめる |
| R04 | アカウントを削除したとき、相手の連携を解除する通知経路がない。相手側に有効な組が残り、次の連携を妨げるおそれがある | **コード確認、実際の削除は要再現。** [DeleteAccountProcessorService](../packages/backend/src/queue/processors/DeleteAccountProcessorService.ts)。削除前後と相手停止中の解除配送を試験する。投稿の削除配送とは別の問題 |
| R05 | 解除後に反対側から同じ組を再連携しようとすると、保存された `initiator` により拒否される。世代更新時には、古い解除の送信待ち・トークンの後始末にも未確認の経路がある | **開始側の制限はコード確認、後始末は要再現。** [LinkService](../packages/backend/src/core/gridspace/GridspaceLinkService.ts)。同じ組の再連携、逆側開始、解除の再送と世代更新を試験する。修正済みの「古い解除通知が新しいトークンを消す問題」とは別件 |

## 実行して確かめる必要がある懸念

次は不具合と断定していない。環境や同時実行の条件を用意して、問題が起きるかを確かめる。

| 懸念 | 必要な確認 |
| --- | --- |
| 代理リアクション・アップロードがトランザクション内で別の DB 接続を使い、接続待ちになる | プールの接続上限を超える同時操作を流し、完了時間と使用接続数を測る |
| 遅れて届いたリアクション要求が、その後の取消を上書きする | 作成・変更・取消の配送順を入れ替える。要求単位の重複防止と、操作順の維持を区別する |
| Redis のメモリ制限でリプレイ防止用 nonce が期限より前に失われる | 本番の `maxmemory-policy` と保持条件を確認する |
| PgBouncer の transaction pooling とセッション単位のロックが両立しない | 本番で PgBouncer を使うか、接続モードが何かを確認する |
| 共有鍵の更新で復号不能になった解除の再送が、後続処理を止める | 鍵の更新・旧鍵の扱いを決め、復号不能な処理が一件あっても他が進むか試す |
| 認可状態の成功応答が切り替わる瞬間に、通知一覧の切替と自動既読が競合する | 初回の通信失敗は修正済み。再認可中に `canReadNotifications` が変わる順序は別途試す |
| 自動フォロー候補の検索、本文検索、管理画面の集計が大きな DB で重くなる | 本番相当の件数で SQL の実行計画、応答時間、必要な索引を確認する |

## 未実装の拡張と、未決・確定済みの仕様

### 機能としてまだないもの

- 旧側の通知を統合して、閉じたブラウザーやアプリにも届ける OS プッシュ。初回公開の必須条件と決まったわけではない。
- 相手側からの即時ストリームによる通知配信。現在は定期取得で動作する。
- 外部監視から運営担当へ自動で知らせる仕組み。管理者がコンパネで確認し、利用者へお知らせする機能はある。
- 通知に付随する、旧側のフォロー申請承認などの全操作の代理実行。未対応の操作は受信元で開く。

### 方針を確定するもの

- **連携を開始できる側。** 現在の backend は R 側からの開始も受け付け、開始側でコピーが動く。G を移行先にする運用に合わせて、R の開始を制限するか、双方向の開始を正式に扱うかを決める。
- **片側だけ連携確定したときの回復。** 現行は相手側の `prepare` で有効化し、別の `commit` 段階を持たない。旧計画の記述をそのまま実装済みとは扱わず、途中停止からの回復条件を確認する。
- **履歴・削除記録の保存、鍵更新、監視と担当。** 本番のデータ量、構成、復旧要件に合わせて運用手順を決める。

### 既に決まっており、未実装と数えないもの

- G だけを使い、R と連携していない人への自動フォロー拡張は、今回の要求に含めない。対象は移行・連携した利用者である。
- フォローは初回だけコピーし、その後は両側で同期し続けない。
- 外部の人には、新アカウントを別にフォローしてもらう。外部向けに旧新 Actor を同一化しない。
- 「連合なし」は Web 全体を非公開にする設定ではない。未ログインへの表示はサーバー・投稿者の設定に従う。G/R 外への ActivityPub 再配送の禁止とは区別する。
- 新旧アカウントが別々に作った投稿を同じ投稿とは扱わない。一方、同じ元 URI の表示用キャッシュについては元投稿の削除を反映している。

## 本番移行までに残る作業

次の順序を提案する。公開条件は運営判断で確定し、まだ実施していない項目を完了扱いにしない。

1. **権限と操作の残件を処理する。** R01〜R05 を先に再現・修正し、解除・ブロック・再連携・アカウント削除・第三者アプリの拒否を回帰試験にする。R07〜R09 の表示・公開範囲も確認する。
2. **同時実行と性能を確認する。** R06・R10 と DB 接続の懸念を扱う。複数プロセス、相手の遅延・停止、本番相当の利用者数・投稿数を使い、通常操作を待たせない条件を定める。
3. **受け入れ条件を整理する。** [06-受け入れ条件](06-受け入れ条件.md) の各項目に、実行するテスト、対象コミット、結果、未確認の理由を対応付ける。CI で再現できる試験と専用ラボで行う試験を分ける。
4. **本番の更新・復元を予行する。** れぞらぶの現在のバージョン、DB、Redis、プロキシ、プロセス構成を確認する。バックアップから復元し、必要な migration と切り戻しを試す。個別 migration の検査だけで DB 全体の復元済みとは判断しない。
5. **運用手順を用意する。** 配送遅延・失敗・容量の監視と連絡先、再試行を止める判断、鍵更新、保存期間、障害時の機能停止方法を決める。修正前の削除記録や投稿者情報がある場合の確認・修復手順も含める。
6. **利用者向けの案内後に段階導入する。** 新旧が別アカウントであること、初回フォローコピー、共有するローカルの範囲、過去投稿の参照、追加認可と旧名義操作を説明する。両サーバーを更新して運営用アカウントで確認し、利用を広げる。

現ラボは PC 上の Misskey とサイト別の PostgreSQL・Redis を `kokopi.me` 経由で公開している。PC の停止・スリープ中も稼働し続ける本番構成ではない。れぞらぶの終了期限も決めていない。
