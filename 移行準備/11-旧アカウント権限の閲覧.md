# 旧アカウントの権限で限定投稿を読む

更新日: 2026-11-12。G/R の両フォークに、追加の OAuth 認可による限定投稿の閲覧・検索を実装した。通常の投稿共有とは別に、投稿元で閲覧者の権限を確認して取得する。

## 利用方法と表示

1. 「設定 → アカウント連携」で本人連携を済ませる。
2. 「両アカウントでの閲覧を許可する」を押し、相手サーバーのアカウントを選んで許可する。これで逆方向も有効になり、相手側から認可をやり直す必要はない。
3. 普段のホームに、旧アカウントの権限で読める限定投稿が混ざる。検索とプロフィールでも通常の投稿一覧に混ぜ、専用の枠や説明を表示しない。設定画面から限定投稿専用の一覧も開ける。

ホームと専用一覧は、現在のアカウントがフォローしている相手と、連携した自分の限定投稿を対象にする。新側で承認待ちでも、旧側に閲覧権限があれば表示する。旧側でフォローが続いていても、新側で解除した相手をホームには戻さない。検索・プロフィールでは、旧側の閲覧権限が残っていれば読める。

ホーム・検索・プロフィールでは通常投稿と同じ日時順に並び、過去へのスクロールを共用する。ホームでは新着ボタンも共用する。投稿元はアカウントのサーバー名で示し、別のサーバー用の欄や表示切り替えは設けない。同じ投稿 URI が両方の取得経路にあれば、現在のアカウントで本文を読める通常投稿を優先する。読めない通常投稿の枠だけがある場合は、旧側の権限で取得した本文を表示する。

両方の取得元が読み終えた日時までを表示し、それより古い行はいったん待機させる。新着取得は投稿元の応答時刻を基準にし、秒精度の ID も考慮して範囲を重ねる。端末の時計には依存しない。20件を超える新着もカーソルで続きを取得する。

フォロワー限定・宛先限定の本文、CW、過去投稿の検索、画像などの添付、投票の内容を読める。返信先・引用元は、旧側で読めるものだけリンクを表示し、開くときも再確認する。人物を指定した検索とプロフィールでは、連携アカウントも対象にする。

新しい追加認可は、G から R を読む許可と R から G を読む許可をまとめて作る。対象は連携した本人の二つのアカウントだけで、それぞれのアカウントが読める範囲を越えて取得しない。本人連携だけでは限定投稿の閲覧を許可しない。追加認可でフォローをコピーし直すこともない。

更新前の片方向の許可は自動で広げない。設定画面に片方向であることを表示し、新しい追加認可を一度行うと両方向に切り替わる。G を主な移行先とする運用は変えず、R 側の検索機能を増やすための変更は行っていない。

## 認可とデータの扱い

- 追加認可は別の OAuth クライアント `/gridspace/v1/private-oauth-client` を使う。閲覧用の `read:gridspace-private` に加え、両方向の許可を作る `read:gridspace-private-reciprocal` を要求する。認可開始・完了は本人のセッションだけで行う。閲覧 API を呼ぶアプリには閲覧用スコープを要求する。
- PKCE、state、ブラウザーの確認値、発行元、ログイン中の利用者、本人連携の ID と世代を確認する。認可開始と解除は同じ利用者ごとに直列化する。
- 相手側のトークンは暗号化して保存する。投稿元はトークンの存在、スコープ、利用者、連携状態、トークンの結び付きを毎回確認する。
- 逆向きには別の閲覧用トークンを発行し、両方向を同じ認可ペア ID に結び付ける。認可状態の更新番号も照合し、解除前に作られた要求があとから許可を復活させないようにする。準備中のペアは閲覧に使えず、開始側の確定と認可セッションの完了を同じ DB トランザクションで行う。
- 相互認可による取得では、相手側にもトークンと認可ペアの存続を確認する。この確認先は DB だけを調べ、さらに問い合わせを繰り返さない。トークンを通常のアプリ連携設定から取り消した場合も両方向の取得が止まる。
- 認可の置き換えと相互認可の解除では、外した結び付きのトークン本体も削除する。連携サーバー用のトークンは署名付き専用経路だけで使い、通常の限定投稿・添付 API では受け付けない。過去の更新で残っていたトークンにもこの制限が適用される。
- 検索結果やページ送りを作る前に、投稿元で旧アカウントの公開範囲、宛先、フォロー、ミュート・ブロック、停止・削除、過去投稿の非表示設定を確認する。表示先でも現在のアカウントのミュート・ブロックとホスト制限を適用する。
- 本文を通常の `MiNote`、共有キャッシュ、検索索引へ保存しない。画面でも通常の投稿キャッシュやローカル保存へ入れない。表示用データは読み取り専用で、投稿元の ID を通常の投稿操作へ渡さない。
- 添付は投稿とファイルの所属を確認したうえで取得し、取得後にも権限を確認する。ブラウザーには認証付き API で内容を渡し、相手の公開ファイル URL は渡さない。応答は `Cache-Control: no-store` とする。

## 失効と障害

「限定投稿の閲覧を解除する」は、本人連携とコピー済みフォローを維持して閲覧許可を止める。返信も許可している場合は「限定投稿の閲覧・返信を解除する」と表示し、返信許可も止める。相互認可の場合は両方向が止まり、進行中の追加認可も破棄する。相手が停止中でも手元の許可を止め、相手のトークン失効は永続化した送信待ち処理から再試行する。

本人連携の解除・世代変更、相手でのトークン取り消し、フォローや公開範囲の変更は、次の取得時に確認する。カーソルは閲覧者・本人連携の世代・追加認可・検索条件に結び付ける。再認可後に古いカーソルは使えない。

表示中は、読み込んだ全ページの投稿 ID を再確認する。間隔はホームで10秒、検索・プロフィール・専用一覧で15秒。検索・プロフィールでは表示待ちの行も、ホームでは表示待ちの行や新着キューも対象にする。API の待機は15秒で打ち切り、取得・確認に失敗したら限定投稿の本文と画像を消し、通常投稿は表示を続ける。ページの非表示・移動時にも限定投稿を消し、戻ったときは再取得する。すでに利用者が見たり保存したりした内容を取り消すものではない。

相手の停止中は限定投稿をキャッシュから表示しない。通信が復旧しても、停止中に取り消した許可は復活させない。

連携専用の通信は HTTP/1.1 を使う。試験環境で標準の `fetch` が HTTP/2 を選び、相互の投稿同期中に権限確認や本文取得が送信待ちになる問題を修正した。待機時間や本文サイズの上限は維持している。実通信での再検証結果は [10-実装状況](10-実装状況.md) に記録した。

## 現段階の範囲

- 閲覧・検索と、旧名義での本文・CW の返信まで。返信への添付、リアクション・投票、通知統合は後続。
- 通常ホーム・検索・プロフィールへの合流は実装済み。取得と権限判定はサーバーが行い、通常投稿と限定投稿の並び順・重複・ページ境界はフロントエンドで統合する。別の API クライアントにはこの表示の統合は適用されない。
- 本文と CW はテキスト表示。MFM の装飾やカスタム絵文字の描画は後続。
- 添付の取得上限は16 MiB。大容量ファイルのストリーミングは後続。
- センシティブなチャンネルは既存の検索側の条件に従い、本人以外の投稿を取得しない。
- 本番の投稿量・同時接続数での性能測定は未実施。

## 旧アカウント名義での返信

限定投稿の「連携先の名義で返信」から送信する。初回は設定画面の「連携先の名義での返信を許可する」で追加の OAuth 認可を行う。`write:gridspace-reply` を明示的に要求し、従来の閲覧許可から自動で投稿許可を増やさない。逆方向に作るトークンは引き続き閲覧専用とする。

送信前に、実際に投稿する旧アカウント、公開範囲、宛先、「連合なし」を表示する。宛先限定の返信は元の宛先と投稿者に限定し、本文のメンションで宛先を増やさない。それ以外はフォロワー限定とする。過去投稿の非表示設定によって限定閲覧となった公開・ホーム投稿にも、公開範囲を広げずフォロワー限定で返信する。「連合なし」は返信先から引き継ぐ。

投稿先は旧アカウントのサーバーで、通常の投稿作成処理と回数制限を使う。表示先に代理の投稿を作らない。送信時にも両側の認可と閲覧条件を確認し、投稿元での権限の取り消しと投稿の保存は DB のロックで順序を決める。表示先で解除を始める直前に投稿元で受理された返信まで取り消すものではない。

送信 ID ごとに受付記録と投稿を同じ DB トランザクションで保存する。同じ ID と内容での再試行は同じ投稿を返し、内容を変えた再試行は拒否する。投稿削除後も受付記録を残し、再試行によって投稿を作り直さない。

画面を離れたときは入力本文と CW を破棄する。未確認の送信 ID だけをアカウント・返信先ごとに `sessionStorage` に残し、同じタブで戻ったときは結果確認を行う。結果が未検出でも、元の送信が処理中の可能性があるため新規送信には切り替えない。確認をやめる操作では、再入力による二重投稿の可能性を表示して確認する。ブラウザーの保存が使えない場合は新規送信を始めない。

この専用経路は設定済みの G/R 間だけで使う。外部サーバーに対しては通常の ActivityPub の公開範囲を維持し、「連合なし」や限定閲覧の本文を外部へ転送しない。旧名義の返信も、外部には旧アカウントの投稿として扱われる。

## API と DB 更新

利用者向けは `gridspace/private-grant`、`gridspace/private-notes`、`gridspace/private-file`。サーバー間は署名付きの `/gridspace/v1/private/{authorize,check,revoke,notes,file}` を使う。

返信用に `gridspace/private-reply` と署名付きの `/gridspace/v1/private/reply` を追加した。`prepare` は投稿名義と宛先の確認、`send` は送信、`status` は送信 ID の結果確認に使う。`status` では投稿を作らない。利用者側のアプリには閲覧・返信の両スコープを要求し、サーバー間用トークンは通常 API で受け付けない。応答は `no-store` とする。`private-grant` の開始時に `withReply: true` を指定すると返信の認可を求め、状態の `canReply` で確認できる。

`1794466348204-GridspaceReplyReceipt.js` は返信の受付記録を追加する。両サーバーで適用する。巻き戻し時は、記録を失ったまま再送を受けないよう返信スコープを持つトークンと準備中の返信認可を削除する。投稿本文は削除しない。

ホームへの合流では `private-notes` に投稿の `uri`、投稿者の `avatarUrl`、走査済みの最古日時 `scannedThrough`、投稿元の取得開始日時 `observedAt` を追加した。走査日時は表示先で除外した行も含み、該当投稿のないページでも続きを読める。DB 変更はない。両サーバーのコードを更新する。

相互認可では `/gridspace/v1/private/{mutual-probe,reciprocal,pair-check}` を追加した。`private-grant` の `mutual` は、両方向の有効性を確認できた場合に `true` となる。相手への接続に失敗した場合、画面では片方向と断定せず通信エラーを表示する。

`1794457466799-GridspacePrivateRead.js` は本人連携に暗号化トークン・失効通知待ち・相手側トークンのハッシュを追加し、認可セッションに目的を追加する。既存の連携へ閲覧許可は付与しない。両サーバーで migration を適用してから更新版を起動する。

`1794458897215-GridspaceMutualRead.js` は認可ペア ID、確定状態、更新番号と、再試行に使うトークン ID・相手の更新番号を追加する。既存の片方向認可は維持する。巻き戻す場合は、相互認可を独立した片方向認可として残さないよう無効化する。
