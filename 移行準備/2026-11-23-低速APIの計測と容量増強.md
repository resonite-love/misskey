# 低速APIの計測と容量増強

2026年11月23日。先行調査は [連携性能の実測と増強案](2026-11-23-連携性能の実測と増強案.md) を参照。

## 実施内容

- GridSpace（prox2 / VM 115）、Resonite.love（prox5 / VM 100）をそれぞれ2 vCPU・3 GiBから4 vCPU・6 GiBへ変更。正常に停止してから起動し、HTTPの正常応答とサーバー連携を確認した。
- PostgreSQLの `shared_buffers` を128 MiBから1 GiBへ変更し、再起動後の値を確認した。
- 両VMの `vm.swappiness=10` を `/etc/sysctl.d/90-misskey-memory.conf` に保存。HTTP worker数は既存の1のまま。今回の増強では、DBやバックグラウンド処理とのCPU競合を減らす。
- 連携チャンネルの旧形式ノートを、同じ閲覧者・同じチャンネルの単位で最大100件ずつ取得する。投稿ごとに異なる会話の権限確認は共有しない。取得前後の閲覧権限確認、削除・ミュート・ブロックの反映を残した。

## 遅いリクエストの調査

管理画面は追加しない。運用者はSSHでログとRedisの診断記録を調べる。

- 応答が1秒以上かかった `/api/` と `/gridspace/v1/` のリクエストが対象。
- 時刻、APIの定型パス、HTTPメソッド、所要時間、ステータス、定型エラーコード・理由、リクエストIDを記録する。
- 連携先への通信は、API別に回数・合計時間・失敗回数を集計する。応答本文の読み込み時間を含む。並列実行分も加算するため、通信時間の合計は全体の所要時間を超える場合がある。
- 本文、クエリ、認証情報、IP、アカウント、ノートIDは記録しない。診断記録を返す公開APIは設けない。リクエストIDは `X-Misskey-Request-Id` レスポンスヘッダーでも確認できる。
- Redisに直近24時間・最大500件を保存し、複数workerから同じ一覧を参照する。保存・参照時に期限切れを削除する。
- 保存処理はHTTP応答を待たせない。未完了の保存が8件に達したworkerでは記録を省略する。Redis障害時の完全な記録は保証しない。
- コンソールにも `api.request.slow` の構造化ログを出す。詳細一覧はRedis、長期保存は運用側のログ収集が必要。

```sh
cd /home/neo/misskey
docker compose exec -T web node scripts/inspect-slow-requests.mjs
docker compose exec -T web node scripts/inspect-slow-requests.mjs --min-ms=3000 --route=timeline
```

API別の件数・合計時間・最大時間・失敗件数と、個々のリクエストをJSONで取得する。集計対象は保存された低速リクエストだけで、全リクエストの平均や成功率ではない。DBクエリ単体やCPU処理の内訳は今回の計測には含めない。

## 計測

LLMチャンネル `asbahu9zer` の30件取得。同じユーザーの既存投稿を読むだけで計測した。

| 条件 | 時間 |
| --- | --- |
| 先行調査・ブラウザー経由、増強前 | 2,382 ms |
| 容量増強後・コード変更前・ブラウザー経由 | 507 ms |
| 容量増強後・コード変更前・VM内HTTP、3回 | 555 / 447 / 415 ms |

測定時刻とサーバー負荷が異なるため、固定倍率の性能保証とはしない。変更後の計測と本番リリース結果は後続の記録で追記する。

## 検証

- バックエンドの型チェック。
- HTTPリクエスト間の計測分離、連携先の本文読み込み時間、定型エラー、秘密情報の非記録。
- Redis上での24時間の期限切れ削除、500件の上限、worker間の参照、保存先障害時の処理上限。
- チャンネル別バッチ、権限の取り消し、削除済み投稿の除外、別会話の権限分離。
REST APIの契約、DBスキーマ、通常のActivityPub連合には変更を加えていない。
