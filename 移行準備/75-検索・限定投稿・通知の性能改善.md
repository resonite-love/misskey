# 検索・限定投稿・通知の性能改善（.31.49）

2026-11-17。れぞらぶとぐりすぺの両フォークが対象。

## 変更

- 検索は、IDで限定した候補に対して本文とCWを照合する。PGroongaの全サーバー分の一致候補を毎回作る処理を避ける。全体検索の候補窓を512件から4096件に広げ、該当が少ない場合の空ページを減らす。ユーザー指定は512件を維持し、作者の索引を使う。
- 限定投稿の投稿者・返信先・引用先について、読み取り先のミュート、双方向ブロック、停止・削除、サーバーブロックをまとめて確認する。未知のユーザーのホスト確認も残す。同じ要求内だけで結果を共用し、次の要求では確認し直す。
- 通知も同じ一括確認を使う。タブ復帰時のvalidateとrefreshの連続取得を、権限確認と新着取得を兼ねるrefresh一回にする。

公開範囲、本人と連携先の認可、読取後の再確認、有効期限、失効時の本文除外は維持する。API形式、ActivityPub、DBスキーマの変更はない。通知の全ID収集と全履歴検索の空ページは完全には解消しておらず、今後の改善対象として残る。

## 検証

れぞらぶの関連バックエンド94テスト、ぐりすぺの関連56テスト、通知フロントエンド11テストを両方で実施。別スキーマの実DBで、一括した権限確認と従来の一件ずつの確認が一致すること、ミュート変更が次の要求に反映されること、古い検索結果に到達すること、非公開の検索結果を返さないことを確認した。型検査、変更ファイルlint、SPDX、locale検査も実施した。

## 測定

デプロイ前後に同じアカウント・同じAPI・同じ条件を各3回測り、中央値を比較する。ブラウザ描画や端末からの通信時間は含めない。投稿増加・キャッシュ・一時的な負荷による変動がある。

デプロイ前の候補実装を別プロセスで呼んだ測定では、ぐりすぺの連携チャンネル30件の本文取得が1212ms・103 SQLから331ms・10 SQLへ減った。この数値はAPI全体の応答時間ではない。

## 残る改善点

- 一致がない検索やユーザー指定の疎な検索は、引き続き空ページと続きカーソルを返すことがある。ユーザー指定「やらかし」は両方とも4ページ目で3件に到達した。全履歴の即時検索や検索終了判定まで解決したものではない。
- 通知一覧は再読込のたびに参照IDを収集する。今回は権限チェックの重複とタブ復帰の二重取得を削減したが、IDの差分更新は未実装。
- れぞらぶの標準 `notes/search` のユーザー指定「A」は6〜10秒だった。今回変更した連携検索とは別の経路であり、標準検索自体の調整は行っていない。

実装コミットはれぞらぶ `80d2f20f72`、ぐりすぺ `7f3694d268`。ぐりすぺのDockerビルドは GitHub Actions `44023833307` で成功。れぞらぶは同じタグからローカルビルドして転送し、両方ともイメージ内のrevisionを照合してから反映した。
