# 連携性能の実測と増強案

調査日: 2026-11-23。対象バージョンは両サーバーの `.31.81`。

## 結論

現在の2 vCPU・3GBのVMには余裕が少なく、CPU待ちと、れぞらぶ側でのスワップ書き出しを確認した。物理ホストには余力があるため、新しい機材を購入する前にVMの割当を増やす価値がある。

一方、連携では投稿ごとの取得と認可確認を繰り返している。ネットワーク往復自体は数ミリ秒だった。増強と取得処理の一括化を組み合わせる案を推奨する。増強だけで遅延がなくなるとは判断していない。

## 対象の症状

https://misskey.grid-space.io/gridspace/channels/asbahu9zer?placement=1

前段のブラウザー測定で、初回一覧取得2,382ms、差分取得の成功例680ms・2,586ms、失敗例8,045msを確認した。失敗応答は `GRIDSPACE_TIMELINE_SESSION_UNAVAILABLE`、reasonは `PEER_UNAVAILABLE`。サーバー側の処理期限8秒と一致する。

VM内のディスクは回転式として見えるが、物理ストレージは両方ともNVMeだった。この表示だけを根拠にHDDが原因とは判断しない。

DockerのWebコンテナには、VMとは別のCPU・メモリ上限は設定されていなかった。

## 資源の観測

- れぞらぶのVM内ロードアベレージは観測時4.28 / 6.71 / 6.38、ぐりすぺは3.47 / 3.87 / 3.65。どちらも2 vCPUに対して実行待ちが多い。
- CPU pressureの5分平均は、れぞらぶ43.87%、ぐりすぺ27.36%。これはCPU使用率ではなく、実行可能な処理がCPUを待っていた時間の指標である。
- れぞらぶでは約15秒のvmstat観測中に数十MBのスワップ書き出しがあった。ぐりすぺでは同じ観測中にスワップの出入りはなかった。
- 物理ホストのロードアベレージは約1〜2、ゲストのsteal timeはほぼ0だった。ホスト全体のCPU不足より、VMへの割当が小さい影響が考えられる。

これらは短時間の観測値であり、常時この負荷という意味ではない。

## サーバー間通信と本文取得

本番と同じ内部HTTPS経路・署名・閲覧資格で、読み取りだけを測定した。認証情報は記録していない。

| 処理 | 観測値 |
| --- | --- |
| ハンドシェイク | 初回17ms、接続再利用時2ms・3ms |
| 連携先チャンネルの一覧取得 | 36ms・18ms・20ms |
| 投稿7件を個別に順番に取得 | 77 / 86 / 96 / 152 / 142 / 246 / 224ms、合計1,023ms |
| 同じ7件を一括検証・取得 | 281ms |

一括取得は、この限定した比較では約73%短かった。ただし実際のタイムラインは4件ずつ並列取得しているため、画面全体が同じ比率で速くなるという結果ではない。

`GridspaceTimelineService.hydratePlacements()` は掲載先の取得、本文取得、掲載先の再確認を行う。`TimelinePlacementSource.bodies()` は連携先の投稿ごとに `GridspacePrivateService.notes()` を呼ぶ。この単位ごとに資格の確認、本文の取得、ミュート等の確認が走る。閲覧権限の確認は必要だが、同一リクエスト内で共通する処理をまとめる余地がある。

## DBとWeb処理の切り分け

同じ実装から生成したチャンネル一覧SQLを、読み取り専用トランザクションでEXPLAIN ANALYZEした。

- 通常の一覧: 実行4.124ms、計画2.975ms。
- 30件のURIに限定した再確認: 実行1.764ms、計画3.039ms。
- インデックスを使用し、TEMPへの書き出しはなかった。

前段の活動サンプルでは同種のSQLが約1.2秒継続していたが、単独・キャッシュが温まった条件では再現しなかった。SQLが常に1秒以上かかるという説明は修正する。負荷時の待ち時間と、複数回実行される処理全体を見る必要がある。

約15秒の追加サンプリングでは、れぞらぶの投稿閲覧判定、ユーザー情報・閲覧判定、フォロー展開処理が実行中に現れた。フォロー展開は最大294ms、ユーザー情報・閲覧判定は最大165msを観測した。単独の特定SQLがすべての遅延を占めるという証拠は得られていない。

10秒ずつのCPUプロファイルでは、Webワーカーが消費したCPU時間はれぞらぶ約1.12秒、ぐりすぺ約0.76秒だった。CPUを使い続ける特定のJavaScript処理は上位に現れず、DB等の待ちを含む状態だった。れぞらぶのmasterは同条件で約2.98秒のCPU時間を消費した。これはサンプルであり、すべてのリクエストの内訳を表すものではない。

計測用に一時的に起動したNode inspectorは閉じ、両コンテナ内の対象ポートが閉じていることを確認した。DB統計拡張は起動設定がなく使えなかったため、設定変更・DB再起動はしていない。

## 推奨する順序

1. **両VMを4 vCPU・6GBへ増強する。** 物理ホストの余力から実施可能な案。れぞらぶは8GBへ一気に増やすとホストの余力が減るため、まず6GBで測り直す。
2. **DBキャッシュとワーカー数を割当に合わせて調整する。** shared_buffersは1GB程度を候補にする。Webワーカーは2を候補とし、DB接続数・メモリ使用量を同時に確認する。れぞらぶのswappinessは10を候補にする。これらは未適用。
3. **チャンネル本文を一括取得する。** 投稿ごとの往復を減らし、同一リクエスト内のユーザー・ミュート判定を共有する。取得前後の権限確認と変更の反映は維持する。
4. **通知・連携状態確認の重複を整理する。** 現状は15秒ごとの連携状態・通知件数確認と、通知一覧自身の取得が別々に動く。タブやウィジェットが増えるほど負荷が増えるため、同じ情報を取得する処理の共通化を検討する。
5. 同じチャンネルで初回表示、差分更新、別タブからの復帰を測り直す。平均だけでなく遅いケースとタイムアウト件数を比べる。

8秒の制限を延ばすだけでは、待ち時間が長くなる問題を解決できない。今回、性能改善の実装・VM割当・DB設定は変更していない。
