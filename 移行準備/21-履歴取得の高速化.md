# 履歴取得の高速化

対象: 2026.11.0-grid-space.5 / 2026.11.0-resonite-love.5

## 変更内容

両サーバーのプロフィール履歴を並列に検索する。最初の検索では投稿IDだけを取得し、表示する投稿が決まってから本文を組み立てる。連携先の著者はユーザーIDで絞り込み、投稿一覧とユーザーURIをまたぐOR条件を避ける。

連携先の本文は、署名付きの `POST /gridspace/v1/notes/read-many` で最大20件を一括取得する。送信側のDB処理と受信側の取り込みは同時4件までとする。返信先など未取得の参照があれば追加取得するため、通信が必ず1回で終わるわけではない。共有済みフラグの不要な再書き込みも省く。

公開範囲、削除、ミュート、ブロック、連携解除は引き続き確認する。限定投稿を一括取得APIへ追加しない。取得失敗時はページの位置を進めず、再試行できるようにする。古いサーバーが一括取得APIを持たない場合だけ従来の個別取得を使う。

## LAN内の通信

`gridspace.peerTransportUrl` を設定すると、サーバー間の通信に指定したHTTPS接続先を使う。省略時は従来どおり公開URLを使う。`peerUrl` は公開URLのまま保持する。署名、Host、TLSのホスト名確認、アカウントURI、ブラウザのOAuth画面も公開URLを使う。

独自証明書を使う場合は、信頼する証明書を `peerTlsCaFile` で指定する。証明書検証を無効にする設定は設けない。証明書の更新時には接続側の信頼する証明書も更新し、アプリを再起動する。相互認可が接続待ちで止まらないよう、使用中のソケット数には上限を設けず、空き接続だけを制限する。

DBは各サーバーで独立させたままとし、テーブルや認証情報を共有しない。通常のActivityPub通信と外部サーバー向けの動作は変更しない。

## 検証

- 署名、再送拒否、取得件数、重複ID、不正な本文、取得失敗、旧版へのフォールバック、取り込み上限の単体テスト。
- 2サーバーでの履歴表示、同一時刻の並び順、ページ送り、過去のローカル限定投稿、通知を発生させない取り込み。
- 所有者、フォロワー、指定宛先、第三者、匿名訪問者の公開範囲と、ミュート、ブロック、連携解除後の動作。

単体テスト63件と上記の2サーバー試験が成功した。同一URIのアカウントキャッシュが複数あるケースも、修正前のエラーと修正後の正常表示を確認した。自己署名証明書を使ったHTTPS試験では、64件の同時相互リクエストと64件の認可確認が完了した。信頼しない証明書と異なるホスト名の証明書は拒否された。

本番の所要時間はキャッシュと同時アクセスで変わる。配備時に同じ利用者・件数のリクエストを複数回計測し、単発の最短値だけで改善率を出さない。

TLS接続とプロキシの設定は [Node.js TLS](https://nodejs.org/api/tls.html#tlsconnectoptions-callback) と [nginx proxy](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass) を参照する。

## 本番配備の確認（2026-11-12）

両サイトを `.5` に更新した。専用のnginxコンテナでLAN内HTTPSを受け、相手VMと自VMからの接続だけを許可した。公開URLは変更していない。履歴取得後に、両方のアプリから相手VMの3443番ポートへの実接続を確認した。

証明書は各VMの `.config/gridspace-tls/` に置き、相手の証明書は `.config/gridspace-peer-ca.pem` に保存した。今回の証明書は2029-02-14まで有効。更新時は相手側の信頼する証明書も交換し、nginxと両アプリへ反映する。秘密鍵はVM内に保持し、リポジトリへは保存していない。

### JITの設定

れぞらぶの履歴検索は、PostgreSQLのJITが大きな待ち時間を生んでいた。同じSELECTを読み取り専用トランザクション内で比較すると、JIT有効時の実行時間は3,460.792 ms、無効時は3.978 msだった。別の送信用SELECTは992.002 msから611.015 msとなり、こちらには検索自体の処理時間も残っている。

両方のMisskey DBに `ALTER DATABASE <DB名> SET jit = off` を設定し、アプリを再起動して接続を張り直した。新しい接続で `SHOW jit` が `off` になることを確認した。DBプロセスの再起動やDBの共有は行っていない。短いクエリではコンパイル費用が効果を上回る場合があることは、[PostgreSQL公式資料](https://www.postgresql.org/docs/15/jit-decision.html)にも記載されている。

### APIの測定

同じ連携プロフィールについて、ホーム・返信・Renoteを含む履歴10件をサーバー内部のAPIから取得した。各行は連続3回の値。ブラウザ描画と、ブラウザからサーバーまでの通信時間は含まない。

| 表示側 | 変更前 `.3` | `.5`・LAN・JIT無効の反映後 |
| --- | --- | --- |
| ぐりすぺ | 9,865 / 2,148 / 1,993 ms | 714 / 856 / 1,140 ms |
| れぞらぶ | 4,346 / 3,996 / 4,570 ms | 223 / 99 / 108 ms |

反映後の表は再起動直後の測定を除く。ぐりすぺでは再起動直後に7,459 msの取得もあり、キャッシュの初期化後も常に同じ速さになるとは限らない。少数回の実測であり、負荷試験や応答時間の保証ではない。

追加で、リアクション・通知・認可解除・操作の単体テスト25件も成功した。Dockerイメージのビルドは両方とも成功し、配備したイメージのコミットと`.5`タグの一致、公開APIのバージョン、両アプリ・DB・Redisの正常稼働を確認した。
