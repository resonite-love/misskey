# 15 連携の運用管理

更新日: 2026-11-12。両サーバーのコントロールパネルに「連携の管理」を追加した。URL は `/admin/gridspace`。ログイン中の管理者だけが利用でき、モデレーターや一般利用者、アプリ用トークンからは管理 API を呼べない。

## 状況を確認する

接続欄は設定済みの相手サーバーへ署名付きの確認要求を送り、接続成功、通信失敗、プロトコル不一致、連携無効を表示する。最後の確認日時と、成功時の応答時間も表示する。「接続できました」は確認要求への応答を意味し、すべての処理の成功を保証しない。

件数と処理一覧は、開いているサーバー側の情報を表示する。相手側に残る処理は相手側のコンパネで確認する。

| 表示 | 確認できる内容 |
| --- | --- |
| アカウント連携 | 有効・準備中・解除済みの件数、エラーの件数 |
| フォロー | 初回コピーの待機・失敗、現在も残っている承認待ち、自動フォローの待機・再試行 |
| 投稿配送と解除 | 配送待ちと再試行、連携解除と限定投稿の認可解除の通知待ち |
| 利用者ごとの連携 | ローカルと相手のアカウント、連携状態、開始した側、世代、エラー |
| 処理一覧 | 対象、状態、失敗理由、試行回数、次回試行日時、再試行の可否 |

概要は画面を表示している間、30秒間隔で更新する。利用者と処理の一覧は「リロード」または絞り込みで更新する。利用者IDで絞り込むほか、連携一覧の「この利用者の処理を見る」で対象を選べる。一覧は20件ずつページを送る。通信に失敗した欄は前の表示を残し、古い情報の可能性を示す。概要だけの更新が成功しても、一覧の警告は消さない。

管理 API は OAuth トークン、暗号化済みの認可情報、限定投稿の本文、添付の取得先を返さない。エラーは定義された形式のコードに制限し、相手が返した任意の本文は表示しない。

## 失敗した処理を再試行する

処理の種類を選び、対象行の「再試行を予約」を押す。確認後、通常のバックグラウンド処理へ戻す。完了まで待ってから一覧を更新すると結果を確認できる。

| 種類 | 手動で再試行できる条件と動作 |
| --- | --- |
| フォローの初回コピー | 現在の連携が有効で、このサーバーから開始した連携の失敗行だけを待機に戻す。表示後に連携の世代が変わった場合は変更しない |
| 連携先の自動フォロー | フォローする人とされる人の連携がともに有効で、このサーバーから開始している場合に、失敗後の待機時間を短縮する |
| 投稿配送 | 失敗後の待機時間を短縮する。表示時の配送バージョンが現在も同じ場合だけ変更する |

解除・取消済みの行や、すでに処理された行を復活させない。再試行時も通常のフォロー処理が現在の権限、手動解除、ブロックなどを確認する。投稿削除で配送バージョンが変わったときは、古い画面からの再試行を受け付けない。

再試行を受け付けた変更と管理ログは同じトランザクションで保存する。ログには操作した管理者、処理の種類、処理IDを残す。条件を満たさず変更しなかった要求は成功扱いにしない。管理画面には、処理済み・実行待ち・再試行できない状態のいずれかである旨を表示する。

解除通知は既存の自動再送を続ける。管理者が認可情報を復元したり、本人の代わりに再認可したりする機能は設けていない。

## 利用者にお知らせする

連携一覧で「この利用者にお知らせ」を押すと、そのローカルアカウントを宛先にできる。タイトルと本文、通常表示またはバナー表示を選び、「宛先と本文を確認して公開」で内容を確認してから公開する。送信には Misskey 標準のお知らせを使う。

宛先を「このサーバーの全利用者」に変更すると全体のお知らせになる。個別宛先の選択が全体公開に変わらないよう、確認画面に宛先を表示する。相手サーバーへのお知らせの複製や自動送信は行わない。個別のお知らせの管理は対象利用者の管理画面、全体のお知らせの管理は既存のお知らせ管理画面で行う。

公開要求が失敗した場合は自動で再送しない。応答だけを受け取れなかった可能性もあるため、既存のお知らせを確認してから再操作する。
