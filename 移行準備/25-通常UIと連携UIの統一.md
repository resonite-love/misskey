# 通常UIと連携UIの統一

2026年11月13日。利用者は、ぐりすぺ・れぞらぶの違いで簡易UIになる箇所をなくし、**見た目と操作の両方**を通常のMisskeyに揃えることを指定した。投稿元サーバーと操作するアカウント名義の表示は残す。

この文書は調査結果と実装の完了条件。`.10` 時点の差を記録している。`.11` の検索修正とヘッダー・リアクション部品の共通化は[26番](26-ユーザー指定検索とチャンネル表示の修正.md)を参照。以下の全項目が完了したわけではない。

`.13` ではタブ復帰時の一覧維持と新着アニメーションに対応した。詳細は[28番](28-タブ復帰と新着アニメーション.md)を参照。

`.14` で通知カード・一覧を共通化し、連携先のフォロー申請を承認・拒否できるようにした。検証範囲と残る差は[29番](29-通知カードと操作の統一.md)を参照。以下の表は調査時点の差を示す。

## 実装方法

1. 通知の表示枠とスタイルを通常・連携で共有する。通常通知の操作処理と連携先への操作処理は、同じ見た目から正しいAPIへ送る。別サーバーのIDをローカルAPIに渡さない。
2. 通知プロトコルに必要な表示情報を追加する。種類ごとの遷移先・操作を確認し、通常の通知にある情報を黙って省略しない。
3. フォロー申請の承認・拒否など、不足する連携操作APIを追加する。連携先が本人の権限、対象、現在の状態を確定時にも検証する。既存の読み取り認可を勝手に書き込み権限へ拡張しない。追加認可が必要な場合は画面から案内する。
4. `MkGridspacePostForm` のチャンネル固定を外し、限定返信でも使う。送信先、公開範囲、宛先、操作名義を保持し、再送時の二重投稿防止を共通化する。
5. 投稿の表示・操作部品を共有し、チャンネルだけにある改善を限定投稿にも適用する。見た目を合わせるために、限定投稿を通常投稿の永続キャッシュやグローバルストアへ入れない。
6. 通知のタブと一覧の挙動を揃え、プロフィール・検索・ホーム・チャンネルから同じ投稿を開いた場合も表示と操作を確認する。

お気に入り、クリップ、スレッドミュート、ピン、削除、翻訳、コピーなどは、通常メニューとの対応表を作って個別に実装する。保存先と操作名義を明示し、任意のAPIを転送する汎用プロキシは設けない。

## 共通の完了条件

- 対応する通常画面と並べて、デスクトップ・モバイルで配置、アイコン、余白、操作、遷移を比較する。
- 通知は種類別、投稿は公開範囲別に検証する。連携済みユーザーと、ぐりすぺだけのチャンネル参加者を区別する。
- 閲覧済み通知の既読、通知フィルター、グループ化、ページ送り、ウィジェットも確認する。
- 旧アカウント名義の操作が新アカウントに誤送信されない。認可解除、ブロック、削除、通信失敗、再送も検証する。
- アニメーションで権限を失った本文を残さない。タブ復帰時は再認可前に限定本文を再表示しない。
- 両フォークへ同じ変更とテストをコミットする。APIの型を再生成し、ビルド・対象テスト・lint・SPDX・locale検査を通してから本番へ反映する。

「通知の見た目を直した」だけでは、この仕様の完了とはしない。未対応の通知種別・操作・画面を記録し、利用者に完了範囲を明示する。
