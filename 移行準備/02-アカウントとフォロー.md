# 02 アカウントとフォロー

状態: R-03、R-04、R-09、R-13 を実現する設計案。フォローは一度だけコピーし、その後は両サイトで独立する。

## アカウントとメンバー

ActivityPub のアカウントは、それぞれの Actor URI のまま残す。内部では新旧のアカウントを結びつけるメンバー識別子を持ち、プロフィール、検索、購読対象をまとめる。表示用のまとまりを、外部向けの投稿者 ID に使わない。

初期案では一つの旧アカウントと一つの新アカウントを一組にする。旧・新それぞれに有効な連携を一件までとし、同じ旧アカウントを別の新アカウントに重複登録できない。ユーザー名や表示名の一致では紐づけない。

## 登録と連携の手順

1. ぐりすぺが連携用セッションを作り、PKCE と `state` を使ってれぞらぶへ認可を要求する。
2. れぞらぶが、許可する読み取り・操作と連携先を本人に示す。
3. ぐりすぺが認可コードを交換し、旧サーバーの API から本人のアカウントを確認する。
4. 新アカウントを作る、または現在ログイン中の新アカウントに結びつける。
5. 両サイトで組の ID と世代番号を確認し、連携を有効にする。
6. 旧フォロー一覧を読み、引き継ぎ処理を開始する。処理済みの対象を記録して再開可能にする。

登録、連携、フォロー取得は別の処理として扱う。途中で失敗しても新アカウントを二重作成しない。既存の新アカウントへ結びつける場合は、そのアカウントにログインしていることも確認する。メールアドレスの一致だけで結びつけない。

ユーザー名が空いていれば同名を提案する。既に使われていれば選び直してもらい、既存の名前を奪わない。旧パスワード、二段階認証の秘密、セッション Cookie はコピーしない。

## 利用許可の扱い

本人確認と継続的なアクセスを区別する。旧側のホーム TL・通知・限定投稿を読み続けるには、必要な利用許可を保持する。旧名義での返信などを含める場合は、読み取りとは別に書き込み権限を要求する。

トークンはサーバーで暗号化して保管し、ブラウザやログへ返さない案とする。鍵は本番設定として別に管理する。必要なスコープは採用基盤の API ごとに確認し、管理者権限や全権限を既定で要求しない。確認した OAuth 実装は `authorization_code` を公開しているため、refresh token がある前提で更新処理を作らない。

認可の取消、失効、旧アカウントの停止、権限変更は再取得時に反映する。取れなくなった旧データは「該当なし」ではなく「再連携が必要」など理由を示す。公開プロフィールの紐づけを残すかは Q-06 とする。

## フォロー引き継ぎ

利用者が見る購読対象と、各サーバーに実在する Follow 関係を区別する。連携時の表示上の引き継ぎは R-09 の要求であり、すべての新規 Follow がその場で承認されるという意味ではない。

| 旧側でフォローしていた相手 | 引き継ぎ案 |
| --- | --- |
| れぞらぶだけの A さん | 旧 A さんを購読対象に残す。新側からの Follow と旧側の読み取りを使う |
| 旧新を連携した A さん | 両方を同じ A さんとして扱い、両アカウントの投稿を購読する |
| 外部の A さん | 外部の Actor URI をそのまま引き継ぐ。新規 Follow の承認状態を確認する |
| 自分の旧アカウント | 新たな自己 Follow を作らず、自分の履歴として表示する |
| ブロック中・停止中の相手 | 自動で制限を解除しない。結果を引き継ぎ状況へ表示する |

鍵アカウントへの新規 Follow は、既存の承認手順を通す。旧アカウントで承認済みだからといって、新アカウントを承認済みとしてデータベースへ直接挿入しない。旧側で読める間は、本人の旧権限で取得して表示を継続する。

表示上は「引き継ぎ済み」「承認待ち」「旧アカウント経由」「失敗」を区別する。件数だけを成功数としてまとめない。

## 連携後の変更

R-13 により、片方で Follow・解除しても、もう片方の Follow 状態を書き換えない。初回コピーの対象一覧を固定し、再試行時に新しい旧側の Follow を追加で取り込まない。コピー後の新側で解除された対象は、遅れたコピー処理でも復活させない。

ぐりすぺのホームはぐりすぺ側の現在の購読対象で絞る。旧アカウントの権限は取得に使っても、旧側の Follow 一覧を継続的な表示条件にはしない。旧ホーム TL を無条件に混ぜると、新側で解除した A さんが残るためである。逆に、コピー後に旧側だけで Follow した B さんを新側へ自動追加しない。

手動で作った関係、初回に取り込んだ関係、コピー処理が追加した関係の由来を残す。連携解除で掃除するものと、本人が明示的にフォロー解除するものを区別する。相手があとから新旧を連携した場合も、ぐりすぺで旧アカウントをフォロー・申請中なら、新アカウントを自動で追加する。すでに連携済みの相手も対象とする。手動の解除・申請取消・却下を優先し、追加済みのフォローは連携解除で削除しない。実装した範囲は [14-連携先の自動フォロー](14-連携先の自動フォロー.md) を参照する。

## ミュート・ブロック

初期案では連携した相手を「この人」としてミュート・ブロックした場合、両方の投稿を画面から除く。相手側のブロックや公開範囲判定も維持する。連携を作り直すことが制限の回避手段にならないようにする。

フォローは取り込み、ミュートだけを取りこぼす状態で全投稿の表示を開始しない。まず制限を読み、その後で TL の引き継ぎを有効にする。外部へどの Actor の Block を送るかは、メンバー表示のブロックとは別に確認する。

## 解除と再連携

連携状態は `未連携 → 認可中 → 引き継ぎ中 → 有効` を基本とし、`再認可待ち` と `解除済み` を別に持つ。サーバー間の対応表と本人の利用許可の状態を混同しない。

解除時は旧権限による取得・操作と進行中のコピー処理を止める。解除前に発行したジョブは世代番号で拒否する。ブラウザとサーバーに残った限定データのキャッシュを無効にする。旧投稿と両アカウントそのものは削除しない。

再連携は新しい世代で始める。再認可だけで Follow を再コピーせず、以前のコピー状態を引き継ぐ。もう一度取り込む操作を提供する場合は本人が明示的に実行し、解除済みの対象を復活させるか確認する。取消済みの権限は無条件に復元しない。
