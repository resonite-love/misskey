## 起動した構成

Misskey 本体はこの PC で動かし、Docker の PostgreSQL と Redis をサイトごとに分けた。`kokopi.me` の SSH リバーストンネルで HTTPS と WebSocket を公開している。PC の停止・スリープ中はアクセスできず、OS 起動時の自動起動は設定していない。

各サイトには `lab_admin`、`lab_author`、`lab_reader`、`lab_locked` がある。パスワードとトークンは各作業ディレクトリの `.config/gridspace-lab-accounts.json` に保存し、Git の管理対象外とした。一般登録は招待制、通常連合の接続先はこの 3 サイトに限定している。

再開・停止・アカウント作成・確認のコマンドは [試験環境の手順](../scripts/gridspace/README.md) にまとめた。DB の既存ボリュームと `.config/gridspace-lab*` を保持して再開する。既存 DB の URL だけを変更しない。

## 今回の利用手順と動作

G に登録してログインし、設定の「アカウント連携」を開く。「連携してフォローをコピー」から R の OAuth 認可画面へ進み、R のアカウントで許可する。G へ戻ると連携先と対象ごとのコピー結果が表示される。登録時の招待制限は従来どおり適用される。

本人確認には認可コードと PKCE を使い、認可を始めた G のアカウント・ブラウザー、state、発行元を照合する。R の許可範囲は本人情報、フォロー、ミュート、ブロックの読み取り。投稿権限や逆方向の代理操作権限は付けない。

コピー対象は最初の連携時に最大 10000 件まで固定する。同じ組を再認可・再連携しても対象を追加せず、G で解除したフォローや取り消した申請を復活させない。ミュート・ブロック・停止済みの相手は省略する。鍵アカウントには G のアカウントから新しい申請を送り、承認を待つ。

G で通常の Follow を作るため、その後の公開・ホーム投稿は通常の ActivityPub 配送とホームの閲覧条件に従う。R 側だけのフォロー変更は G へ反映しない。ローカル限定投稿の共有、R の過去投稿の統合、連携済みの相手の二つの Actor への購読展開は、今回の範囲には含めない。

連携は片方から解除できる。コピー済みのフォローは残り、未処理のコピーと保管した OAuth トークンを無効にする。相手サーバーへ解除を通知できない場合は、画面に通知待ちを表示して再送する。通常の Follow が残る相手からの投稿は、連携解除後もホームに届く。

## 保存と再開

追加したテーブルは `gridspace_link`、`gridspace_auth_session`、`gridspace_import_item`、`gridspace_follow_override`。二つの新規 migration で作成する。連携 ID と世代、最初のコピー対象、対象ごとの処理結果、利用者のフォロー取消時刻を保存する。

処理待ちのコピーはバックグラウンドで再開する。通常の Follow 操作と取消操作は利用者単位で排他し、取消記録を先に確定する。暗号化した OAuth トークンと PKCE verifier はサーバー内だけに保存し、期限切れの認可セッションは削除する。暗号化には環境変数の peer キーから用途別に導出した鍵を使うため、キー変更時は利用者の再認可が必要になる。
