## 起動した構成

Misskey 本体はこの PC で動かし、Docker の PostgreSQL と Redis をサイトごとに分けた。`kokopi.me` の SSH リバーストンネルで HTTPS と WebSocket を公開している。PC の停止・スリープ中はアクセスできず、OS 起動時の自動起動は設定していない。

各サイトには `lab_admin`、`lab_author`、`lab_reader`、`lab_locked` がある。パスワードとトークンは各作業ディレクトリの `.config/gridspace-lab-accounts.json` に保存し、Git の管理対象外とした。一般登録は招待制、通常連合の接続先はこの 3 サイトに限定している。

再開・停止・アカウント作成・確認のコマンドは [試験環境の手順](../scripts/gridspace/README.md) にまとめた。DB の既存ボリュームと `.config/gridspace-lab*` を保持して再開する。既存 DB の URL だけを変更しない。

## 今回の利用手順と動作

G に登録してログインし、設定の「アカウント連携」を開く。「連携してフォローをコピー」から R の OAuth 認可画面へ進み、R のアカウントで許可する。G へ戻ると連携先と対象ごとのコピー結果が表示される。登録時の招待制限は従来どおり適用される。

本人確認には認可コードと PKCE を使い、認可を始めた G のアカウント・ブラウザー、state、発行元を照合する。R の許可範囲は本人情報、フォロー、ミュート、ブロックの読み取り。投稿権限や逆方向の代理操作権限は付けない。

コピー対象は最初の連携時に最大 10000 件まで固定する。同じ組を再認可・再連携しても対象を追加せず、G で解除したフォローや取り消した申請を復活させない。ミュート・ブロック・停止済みの相手は省略する。鍵アカウントには G のアカウントから新しい申請を送り、承認を待つ。

G で通常の Follow を作り、その後は G の現在の購読条件でホームを表示する。R 側だけのフォロー変更は G へ反映しない。連携した自分のもう片方のアカウントの公開・ホーム投稿も表示する。他のメンバーが二つのアカウントを連携したとき、その両方を自動で Follow する機能はまだない。

連携は片方から解除できる。コピー済みのフォローは残り、未処理のコピーと保管した OAuth トークンを無効にする。相手サーバーへ解除を通知できない場合は、画面に通知待ちを表示して再送する。通常の Follow が残る相手からの投稿は、連携解除後もホームに届く。

## 共通 LTL と投稿の見え方

`gridspace.enabled` を有効にした G と R で、更新後の公開・ホーム投稿を共有する。本人連携していない投稿者も対象になる。公開投稿は相手側の LTL とソーシャルに入り、ホーム投稿は購読条件に合うホームだけに入る。フォロワー限定、ダイレクト、チャンネル投稿はこの共有の対象外とした。

例えば G の kokoa さんの発言は、R でも G のアカウントによる投稿として表示する。R の kokoa さん名義の投稿を作る処理はない。投稿元の Actor URI、投稿 URI、日時を保ち、通常の ActivityPub と重なったときは同じ URI で重複を防ぐ。

ローカル限定投稿では `localOnly` を保持し、返信・引用・Renote にも引き継ぐ。通常の ActivityPub 配送と ActivityPub での取得は禁止したまま、固定した相手サーバーへ署名付きの専用通信で渡す。Web での閲覧は従来のログイン要求などに従い、`localOnly` を Web 全体の非公開設定には読み替えない。

投稿元で削除すると、相手側でのその投稿の表示も取り下げる。アカウント削除時も、そのアカウントが投稿した内容の表示を取り下げる。連携先の別アカウント自体や、別アカウントが書いた投稿を削除する機能ではない。

画像、CW、投票の初期内容を受信できる。ローカル限定投稿へのリアクションと投票結果の相互反映はまだ実装していない。過去投稿はプロフィールの履歴、横断検索、返信・引用の参照先から取得する。全履歴の事前複製は行わない。

## プロフィールと過去履歴

連携した人のプロフィールカードの直下に、連携先のアイコン・表示名・サーバー名を含むアドレスを表示する。クリックすると連携先のプロフィールへ移動できる。ノート一覧にも両方のアカウントへのリンクを表示する。連携済みのプロフィールでは両アカウントの読める投稿を元の日時順に並べる。投稿元は通常のアカウント表記とサーバーバッジで示し、「〜からの投稿」という追加の行は表示しない。利用者向けの表示切り替えは設けない。ハイライトは元のアカウント別表示を維持する。

過去のローカル限定投稿も、必要なページを相手へ問い合わせて取得する。新着通知、アンテナ通知、活動チャートを履歴取得で発生させない。同じ本文の別投稿、同じ短い ID を持つ別サーバーの投稿、Renote は別々に扱い、同じ投稿 URI だけを重複として扱う。

相手サーバーへ問い合わせる履歴は公開・ホーム投稿に限る。それに加え、閲覧中のサーバーに保存済みの投稿から、今ログインしているアカウントで読めるフォロワー限定・指名投稿を表示する。通常の連合で届いた連携先の限定投稿も対象になる。取得後にも閲覧権限を確認するため、ページ送りの途中でフォローを解除すると、その後のページにはフォロワー限定投稿が出なくなる。

チャンネル投稿は「全て」に含め、「ノート」「ファイル付き」には含めない。センシティブなチャンネルの投稿は通常のプロフィールと同様に投稿者本人だけに表示する。ユーザー・チャンネルのミュート、期限切れのチャンネルミュート、ブロック、未ログイン閲覧設定も適用する。

標準の履歴 API は旧アカウントの閲覧権限を代行しない。追加認可を受けた利用者は、別の専用 API で旧アカウントの権限を確認して限定投稿を読む。限定本文は通常の投稿データベースや検索索引に取り込まず、認可した利用者の画面だけに表示する。詳細は [11-旧アカウント権限の閲覧](11-旧アカウント権限の閲覧.md) を参照。

ページ送りは両取得元の最初の上限と、最後に読んだ位置を保持する。新着は再読み込み時に取得し、途中のページへ割り込ませない。カーソルは閲覧者、対象プロフィール、表示条件、連携 ID と世代に結びつけ、1 時間で失効する。連携先の停止中は取得位置を進めず、再試行できる。アカウント別一覧は引き続き利用できる。

利用者向け API は `gridspace/member` と `gridspace/history`、署名付きの内部 API は `POST /gridspace/v1/history`。`gridspace/history` の `withChannelNotes` は既定値を `true` とし、この指定を相手サーバーへは送らない。保存済みの限定投稿を含める変更に伴い、旧版の履歴カーソルは再読み込みを必要とする。履歴は一度に最大 20 件を返し、参照先の取得にも共有の件数予算を設ける。取り込みは同時に最大 4 件、ノート・参照先の取得予算は 64 回とし、15 秒を過ぎたら新たな取得を始めない。添付取得やロック待ちを含めた処理全体が 15 秒で終わる保証ではない。新しい DB migration は不要。

## 保存と再開

本人連携用のテーブルは `gridspace_link`、`gridspace_auth_session`、`gridspace_import_item`、`gridspace_follow_override`。連携 ID と世代、最初のコピー対象、対象ごとの処理結果、利用者のフォロー取消時刻を保存する。

共通投稿用に `note.gridspaceShared`、`gridspace_note_delivery`、`gridspace_note_tombstone` を新しい migration で追加した。投稿と送信待ち情報は同じトランザクションで保存する。相手の停止中は送信待ち情報を残し、復旧後に自動で再送する。本文の古いコピーを送り続けず、受信側が投稿元の現在の内容を取りに行く。削除記録は再送による復活を防ぐために保持する。

処理待ちのコピーはバックグラウンドで再開する。通常の Follow 操作と取消操作は利用者単位で排他し、取消記録を先に確定する。暗号化した OAuth トークンと PKCE verifier はサーバー内だけに保存し、期限切れの認可セッションは削除する。暗号化には環境変数の peer キーから用途別に導出した鍵を使うため、キー変更時は利用者の再認可が必要になる。

## 人物・過去投稿の横断検索

検索画面では既定で「両サーバー」を検索する。人物は表示名とユーザー名、投稿は本文と CW の部分一致を使う。大文字・小文字は区別しない。通常の検索範囲も引き続き選べる。横断検索の対象は二つのサーバーを原産とする内容で、外部サーバー全体の検索ではない。

人物の検索結果には、一致したアカウントと確認できた連携先を表示する。旧・新のどちらの名前でも探せる。同名だけでは同一人物と扱わない。人物を指定した投稿検索では、連携が有効なら両アカウントを検索する。

相手にしかない公開・ホームの過去投稿は署名付きの専用 API で探し、表示する分だけ取得する。ローカル限定投稿も対象だが、通常の ActivityPub や E へは渡さない。標準の検索 API は、保存済みの限定投稿を現在の閲覧権限で検索する。追加認可がある場合は、旧側にしかない限定投稿も別の認証付き API で検索し、専用欄に表示する。

検索語への一致を返す前に、投稿元と閲覧側のバックエンドで公開範囲、ミュート・ブロック、停止・削除、ログイン要求、過去投稿を隠す設定を確認する。フロントエンドだけで本文を隠す方式ではない。過去投稿をフォロワー限定にする設定が適用された投稿も、共通キャッシュへの新規取り込みから除外する。ハードミュートは通常の投稿表示と同様に画面へ適用する。

投稿は元の日時順に並べ、各サーバーの最初の上限を保持してページを送る。検索語、日時範囲、指定人物、閲覧者、対象人物の連携 ID・世代が変わると古いカーソルを使えない。片側の停止時は取得できた結果を暫定表示し、カーソルを進めない。再試行が成功すると暫定分を正式な次ページに置き換える。

横断検索は索引の有無に依存しない SQL 検索とした。通常検索の Meilisearch 設定は変更していない。1 ページは最大 20 件、SQL 1 回は 3 秒、検索の相手側通信は 1 回 8 秒で打ち切る。履歴本文の取得には既存の取得数・開始期限を使う。本番の投稿量での性能測定と、処理全体の所要時間の評価は未実施。

## 旧名義での返信

限定投稿の「連携先の名義で返信」から、旧アカウント名義で本文・CW を投稿できる。最初に設定画面で返信用の OAuth 許可を追加する。既存の閲覧許可だけでは投稿できず、逆方向の許可も閲覧専用のままとする。

送信前に投稿名義・公開範囲・宛先を表示する。宛先限定の参加者と「連合なし」を維持し、本文のメンションによって宛先を広げない。フォロワー限定への返信は旧アカウントのフォロワー限定とする。サーバー間の再試行で投稿を重複させず、削除後の再試行でも投稿を復活させない。

画面を離れると入力本文・CW を破棄し、未確認の送信 ID だけを同じタブに残す。再読み込み後は新しく送らず、旧サーバーの受付記録で結果を確認する。仕様と解除・障害時の扱いは [11-旧アカウント権限の閲覧](11-旧アカウント権限の閲覧.md) に記載した。

これらの拡張は設定した G/R 間でのみ動作する。外部サーバーとは通常の ActivityPub で通信し、旧新アカウントをそれぞれ別の Actor として扱う。

検証中、別プロセスで受信したブロックの変更が API のメモリキャッシュに最大 1 分残る既存の挙動が見つかった。ブロックの内部イベントで各プロセスのキャッシュを破棄するよう修正した。

## 計画上の位置と次の作業

T00 の試験基盤に OAuth の許可・失効と初回コピーの結合試験を追加した。既存の二台向け連合試験は変更していない。

T02 は認証に加えて連携の永続化・世代・解除再送を実装した。`POST /gridspace/v1/handshake` は `account-link-follow-copy`、`community-notes`、`member-history`、`community-search` を返す。公開メタデータは `GET /gridspace/v1/oauth-client`、署名付きの内部 API は `POST /gridspace/v1/link/{identity,prepare,check,revoke}` と `POST /gridspace/v1/notes/{read,sync}`、`POST /gridspace/v1/history`、`POST /gridspace/v1/search`。通常クライアントは本人のセッションで `POST /api/gridspace/link` の `action` を指定する。投稿用の送信待ち処理は実装済みで、通知の統合は未実装。

T03 は登録後の連携画面、T04 は Actor ごとの初回コピー、T05 はプロフィール履歴と旧アカウントの権限による限定投稿の閲覧まで実装した。T06〜T08 は新規投稿の共通表示に加え、限定投稿の通常ホームへの合流まで実装した。T09 は人物・過去投稿の横断検索と、追加認可による限定投稿の検索まで実装した。旧名義での操作は本文・CW の返信まで実装した。返信への添付、リアクション・投票、登録画面への案内、連携済み Actor の購読展開、通知統合、運用監視と負荷試験は残っている。全体の完了条件は [09-実装計画](09-実装計画.md) と [06-受け入れ条件](06-受け入れ条件.md) を維持する。

CHANGELOG 候補: 追加の投稿許可により旧アカウント名義で限定投稿へ返信できるようにし、再送と画面の再読み込みによる二重投稿を防止した。
