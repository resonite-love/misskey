# Unified notification timeline

`POST /api/gridspace/notifications/timeline` is a first-party authenticated-session API (`secure: true`). Existing notification APIs and scopes remain unchanged. The response is private/no-store. Fetching never marks notifications read.

- `mode=page` creates or continues an immutable snapshot; `limit` is 1–40. Cursors bind the viewer, exclusions, snapshot, position and page size with a random secret/HMAC. Concurrent retries select the same references and next cursor. Deleted or newly unauthorized rows leave holes; they do not move that boundary.
- `mode=validate` rechecks the first `count` references of that snapshot. `mode=refresh` creates a fresh snapshot, retaining at least the old loaded boundary when its reference still exists. `scannedCount` counts references, including filtered or deleted rows. The browser preserves server order and never compares source cursors.
- Source reference acquisition is bounded to 2,000 inbox records per source (the existing default retention is 500). The signed peer `notifications/references` route checks the notification grant/channel identity before and after acquisition, and returns only ID and creation time. Exclusions apply before snapshot ordering. Over-bound sources are reported unavailable instead of silently truncated.
- Sort order is creation time descending, then complete source/origin/recipient/notification identity descending by binary string comparison. Equal short IDs from different inboxes remain distinct. Grouping adjacent reactions/renotes and local hard-mute presentation remain client responsibilities.
- Redis stores only reference identity, timestamps, exclusion hash input, authorization fingerprints, cursor secrets and expiry. No notification body, note, actor or attachment URL is copied into the snapshot. Snapshots expire after 30 minutes; an atomic Lua operation retains at most eight per viewer. Missing/expired state returns `CURSOR_EXPIRED`; tampering, another viewer or changed exclusions returns `CURSOR_INVALID`.
- Every delivery rechecks the local link/channel binding, fetches the selected IDs through the existing authorization and visibility filters, and checks the binding again. A failed source contributes no bodies and has `unavailable`/`unauthorized` status and an unknown count. Other sources remain usable; refresh can recover the source. There is no unattended per-user polling worker.
- Source work has an eight-second request deadline and a 640 KiB body budget per source. `revalidateAfterMs` is the remaining portion of a ten-second lease measured from server-request start. Clients use their own request start conservatively, strip protected content at expiry even during a pending request, and strip it immediately when hidden. Loading an older page does not extend the lease of existing rows.
- Explicit read operations remain on `gridspace/notifications/read`. The client sends source, origin, recipient and actual visible IDs; these optional identity fields are validated before writing, including on the signed peer route. A channel identity only changes eligible reactions in its own channel inbox. All-read stays explicit, is serialized behind pending seen writes, and invalidates concurrent stale read snapshots. Read confirmations use full row identity.

Tests: `notification-timeline.test.ts`, `notification-timeline-redis.test.ts`, `notifications.test.ts`, and frontend `gridspace-notifications.test.ts` cover stable ordering/replay, bounded Redis state, expiry, altered/foreign cursors, source failures, revocation, exclusions, body stripping, new-item queues and read races. Redis snapshots are not a durable inbox or an event log; a refresh discovers the currently retained source inboxes.
