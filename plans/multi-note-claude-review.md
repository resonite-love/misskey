# Multi Note 保存形式：Claude設計レビュー

- レビュー日: 2026-11-21
- 方法: Claude Code（Opus、読み取り専用）に両リポジトリの計画書と実コードを渡し、設計上の問題を指摘してもらった。以下はコードで再確認した要点と対応案。
- 状態: 設計レビュー。実装コードは未変更。

## 結論

「原本1件＋掲載表」という骨格と、段階1で ActivityPub の形式を変えない方針は妥当。一方、新方式のチャンネル専用原本を `note.channelId=null` にする案は、旧コードが `channelId IS NULL` を通常投稿と読むため、修正漏れが公開面への混入に直結する。新しい書き込みを有効にする前に、保存形式と配備・ロールバック条件を決め直す必要がある。

## 優先度の高い指摘

1. **通常経路への混入**：`NoteCreateService.pushToTl` は `channelId` がなければ通常fanoutを行う。LTL/GTL/HTL/ユーザー一覧などのDB取得と対応ストリームも同じ前提。計画の対象表から `roles/notes.ts`、`antennas/notes.ts`、`Poll.channelId` と `notes/polls/recommendation.ts` が漏れていた。アンケート推薦は `excludeChannels=true` のとき `poll.channelId IS NULL` でチャンネル投稿を除外するため、新形式のチャンネル専用アンケートを誤って含める。
2. **ぐりすぺ連携からの露出**：`canShareGridspaceNote` は `channelId=null` と `public/home` を通常共有の条件にする。作成時の `gridspaceShared` に加え、`GridspaceNoteService.read()`、`GridspaceSearchService`、`GridspaceActionService` も同じ前提を持つ。段階1のローカル複数掲載を公開する前に、これら全経路で通常投稿先の有無を確認する必要がある。
3. **旧版への切り戻し**：新方式のチャンネル専用原本が残ったまま旧版のアプリへ戻すと、旧版はそれを通常投稿として読む。新規書込を止めるだけでは防げない。現行の `channelId=null` 案を採るなら、書込開始後は旧版へ戻せない運用制約を明記する。
4. **返信とRenote**：新方式の親では `channelId=null` なので、現行の返信処理がチャンネル文脈を外す。親がチャンネル専用なら `NoteCreateService.create()` 内で返信の通常投稿先なし・ローカル限定を確定する。APIだけの対策では旧クライアント、ぐりすぺ返信、予約投稿を覆えない。引用・Renoteを `NoteCreateService` 全体で拒否すると、連合から届く Announce の受信も壊れる。ローカル操作と連合受信を分ける。
5. **書込後の整合**：原本のDB挿入後、fanout・チャンネル件数・検索索引は非同期で動く。原本と掲載表と冪等記録をトランザクションに入れても、後続処理の失敗は残る。掲載先ごとの処理を再実行できる永続ジョブにし、再送時に二重集計しない。

## 保存形式の代案と注意点

Claudeは、チャンネル専用原本の `note.channelId` に代表チャンネルを入れ、掲載表に全チャンネルを記録する案を提示した。この場合、旧版の `channelId IS NULL` 判定からチャンネル専用原本が漏れず、旧クライアントにも単一チャンネル投稿として見える。通常＋チャンネルは `channelId=null` のままにできる。

ただし、そのまま採用できない。既存の `note.channelId` 外部キーはチャンネル削除時に **ON DELETE CASCADE** で原本を削除する。代表チャンネルを掲載解除した後も旧列に残すと、旧版では解除済みチャンネルに表示される。代表チャンネルの削除、全掲載先の解除、原本の存続をどう扱うかを決め、必要なら新migrationで参照制約を変える。`includeDefault` を残すかも、この判断と合わせて決める。

現行案を維持する場合は、通常経路の判定を共通化し、素の `channelId IS NULL` を新規投稿の判定に使わないことをCIで検出する。ぐりすぺの通常共有とポーリング推薦を含む全経路の修正を、書込有効化の前提条件とする。

## 追加の実装注意

- チャンネル一覧の現在の `note.channelId NOT IN (...)` は、新形式の `NULL` に対してSQLの3値論理で行を落とす。ミュート条件を掲載先単位に組み直す。
- チャンネル一覧を原本表から `EXISTS` で探す案は、投稿が少ないチャンネルで高コストになり得る。掲載表の `(channelId, noteId DESC)` 索引からページングするクエリを比較する。複数チャンネルをまとめるホームでは、通常投稿経路と掲載経路を別々に絞って統合する案を検討する。
- SQLとMeilisearchの通常検索は現状、旧チャンネル投稿を一律に除外していない。新形式だけを通常検索から除くと挙動が分かれる。検索方針を先に決め、Meilisearchの再索引を配備手順に含める。
- センシティブ語と `canPublicNote` による `home` への変更は現在 `channel == null` の場合だけ。新形式のチャンネル専用投稿を旧単一チャンネルより厳しくするかを仕様として決める。
- `NoteEntityService.packMany` とRedisからのDB再取得で掲載表をまとめて読み、WebSocketとミュートにも使う。チャンネルのピン留め、ランキング、通知、プロフィールも掲載先単位で確認する。

## 実装前の判断

まず「`channelId=null`＋`includeDefault`」と「代表チャンネルを旧列に残す」案を、チャンネル削除・掲載解除・旧版への切り戻しまで含めて比較する。その後、返信の表示先、通常＋チャンネル投稿のRenote可否、通常検索、ミュート、ピン留めの仕様を確定する。どちらの保存形式でも、ぐりすぺの通常共有判定を段階1の必須修正として扱う。
