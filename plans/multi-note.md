## 公開条件と今回の範囲（2026-11-21）

「チャンネルだけ」は通常TL・通常RSS・通常共有・連合へ配信しない指定とする。原本URL、標準API、会話詳細、添付URLは既存の公開チャンネルと同じ条件で扱う。掲載解除は一覧・当該ホーム経路・ピン・集計から外す操作であり、本文や添付を非公開にする操作ではない。全掲載が消えても通常配信へ切り替えず、原本は既存の公開条件で残る。原本を消す場合は原本削除を使う。

今回必須は保存/配信先の分離、既存の閲覧制限、用途別の書込権限、削除・退会・再送対策、新方式の返信/反応/投票/添付/通知、一覧のURI統合、作成結果不明時の復旧。公開URLの完全失効、添付配信基盤の認可付きURL化、未掲載原本の本人限定化、既存全履歴の返信修復、通常AP投票全体の排他再設計、匿名証明の新基盤は後回しにする。新方式で会話や操作を壊さない確認は延期しない。

詳細な必須M1〜M8・後回しD1〜D5とAstra指摘の扱いは、ぐりすぺ側 `plans/multi-note-placement-protocol.md` に集約する。過去レビューの原文は変更せず、厳密な掲載失効を前提とした指摘は本方針で再分類する。

Multi Noteの予約投稿と投稿後の掲載先追加・再追加は要件から除外し、将来対応の残件にしない。公開センシティブチャンネルも掲載先に選べる要件とし、必要なCWは投稿者が付ける。原本のCWを全掲載先で共用し、自動付与・入力必須化・掲載先別CW・センシティブ属性の混在による選択制御は追加しない。一律除外の撤去を両リポジトリに実装し、追加20件と従来48件の実サーバー受け入れテスト、両方向のブラウザ操作で検証済み。

## 目的と採用する概念

投稿欄から普段の投稿とチャンネルを身近に選べるようにする。利用者が複数チャンネルを選んでも、本文、投稿の恒久的なURI、返信の会話、リアクションの対象は1つにする。

概念は「投稿に掲載先を付ける」。投稿の原本は投稿者のホームサーバーが持つ。各チャンネルは原本を指す掲載記録を持ち、チャンネルのタイムラインには同じ投稿を表示する。相手サーバー上の保存用IDは異なっても、原本URIを共通の識別子にする。

```text
投稿の原本（1 URI、1会話、1つのリアクション対象）
  ├─ 通常の投稿先（選択可能）
  ├─ れぞらぶ #A への掲載
  ├─ れぞらぶ #B への掲載
  └─ ぐりすぺ #C への掲載
```

## 段階と初期範囲

| 段階 | 提供する体験 | 実装上の境界 |
| --- | --- | --- |
| 1 | 通常の投稿と同一サーバー内の公開チャンネルを自由に組み合わせ、1投稿・1会話として掲載。チャンネルだけの投稿も可能 | 連携先チャンネルは段階2で扱う。公開センシティブチャンネルのCWは投稿者が設定。既存の単一チャンネル投稿は継続 |
| 2 | れぞらぶとぐりすぺのチャンネルを同じ投稿先選択画面で選ぶ | 署名付き連携、原本URI、認可、再試行、連携先の掲載解除を追加 |

旧段階3の予約投稿と投稿後の掲載先追加・再追加は撤回する。失敗した当初の掲載要求の再試行、掲載解除、原本削除は必要な操作として維持する。

段階1でもCW、添付、アンケートを1つの投稿として扱う。返信・引用・Renoteを作成しながら複数チャンネルへ掲載する操作は対象外とし、既存の投稿操作を維持する。返信は親の掲載先を複製しない。チャンネル専用の親への返信は会話内だけに置き、各チャンネルの一覧には独立した行を出さない。返信欄には「この返信は共通の会話に表示されます」と示す。通常投稿先を含む親には既存の通常返信ルールを使う。

チャンネル数に固定上限は設けない。選択数は表示し、候補が多い場合は検索と選択済み一覧で確認できるようにする。APIは重複した投稿先を拒否し、既存の投稿頻度制限を維持する。多数の掲載先へのfanoutは分割処理し、通常投稿と同じノートIDを使う。

## Web UI 仕様

### 投稿欄の配置

既存の投稿欄の本文より上、アカウント・公開範囲表示の下に「投稿先」を置く。通常の投稿欄では「通常の投稿」を初期選択し、チャンネルを追加しても自動では外さない。チャンネル画面から開いた場合は、そのチャンネルだけを初期選択し、「通常の投稿」を追加できる。最後の投稿先は外せない。投稿先の内訳、公開範囲、連合の有無を送信前に示す。

チャンネルを1件以上選ぶ投稿の公開範囲は `public` に限る。現在の公開範囲が `home` / `followers` / `specified` の場合は、チャンネルを選んでも自動で公開範囲を広げない。選択を保持したまま送信を止め、利用者が公開範囲を変更するかチャンネルを外す。チャンネルだけの投稿は既存と同じく連合しない。通常の投稿も選んだ場合は既存の連合ON/OFF設定を尊重し、連合ONなら原本の通常投稿だけが連合する。チャンネルへの掲載はローカルのまま扱う。

```text
デスクトップ：投稿ダイアログ
┌──────────────────────────────────────────────┐
│ [自分のアイコン]  パブリック  連合ON         [投稿] │
│ 投稿先 [通常の投稿] [#A ×] [#B ×]           [変更] │
│ 通常の投稿と2件のチャンネルに掲載・連合します       │
│ ┌──────────────────────────────────────────┐ │
│ │ 本文 / CW / 添付 / アンケート               │ │
│ └──────────────────────────────────────────┘ │
│ [添付] [アンケート] [CW] [絵文字]                   │
└──────────────────────────────────────────────┘

モバイル：投稿ダイアログ
┌──────────────────────────┐
│ [戻る] 公開             [投稿] │
│ 投稿先 [通常] [#A] [#B] [変更] │
│ 通常の投稿＋2チャンネル    │
│ 本文                         │
│ …                            │
│ [添付] [CW] …                │
└──────────────────────────┘
```

「追加」または「変更」で投稿先シートを開く。デスクトップはダイアログ、モバイルは全高に近いシートにする。最上部に「通常の投稿」のチェック項目を固定し、その下に検索入力と「お気に入り」「フォロー中」「最近使った」「検索結果」を置く。各チャンネル行に名前、発信元、説明の先頭、センシティブ表示、選択状態を示す。発信元は同名チャンネルの区別に使い、色だけに頼らない。既存の `channels/my-favorites`、`channels/followed`、`channels/search` と連携先の `gridspace/channels` を候補取得に使う。段階1では連携先の行を選択不可とし、「連携先への掲載は準備中」と示す。

```text
投稿先を選ぶ
┌──────────────────────────────────────┐
│ チャンネルを検索…                    │
│ [✓] 通常の投稿                       │
│ お気に入り                           │
│ [✓] #A    れぞらぶ  短い説明         │
│ [ ] #B    れぞらぶ  短い説明         │
│ [ ] #C    ぐりすぺ  連携先への掲載は準備中 │
│                                      │
│ 2件選択                [投稿欄へ戻る] │
└──────────────────────────────────────┘
```

### 操作と状態

| 場面 | 表示・操作 |
| --- | --- |
| 通常の投稿欄から開く | 「通常の投稿」を選択済み。チャンネルを追加しても選択を保つ |
| チャンネル画面から開く | そのチャンネルだけを選択済み。通常の投稿やほかの適格チャンネルを追加できる |
| 投稿先が0件になる操作 | 最後の投稿先は外せない。理由を表示し、本文と選択を保持する |
| 公開範囲が `public` 以外でチャンネルを選択 | 公開範囲を自動変更せず送信を止め、変更またはチャンネル解除を案内する |
| 選択中 | チップを押して解除。投稿先シートではチェックボックスで選択。選択数と連合の有無を本文の近くに表示 |
| アーカイブ・権限失効・ブロック・ミュート | 候補を選択不可にし理由を表示。送信直前にもサーバーで再検査 |
| 公開センシティブチャンネル | センシティブ属性だけで選択・混在を拒否しない。必要なCWは投稿者が既存のCW欄で設定し、全掲載先で共用する |
| 送信中 | 投稿ボタンと投稿先編集をロックし、再押下で二重投稿しない |
| 送信成功 | 投稿詳細へのリンクを一つ表示し、掲載先チップを添える。下書きは成功確認後に削除 |
| 一部の連携先だけ失敗（段階2） | 原本は保持。「#Cへの掲載に失敗」と明示し、その掲載だけ再試行する。本文の再投稿はしない |
| 連携切れ・通信不能 | 既存の選択と本文を保持し、再認証または再試行への導線を出す |

投稿詳細、チャンネル一覧、プロフィールでは同一投稿IDを使う。同じ利用者が掲載先の複数チャンネルをフォローしていても、ホームのタイムラインは1行にまとめ、閲覧できる掲載先だけをチップで示す。投稿メニューには投稿者向けの「掲載先を見る」と「掲載を外す」を設ける。チャンネル管理者による掲載解除はそのチャンネルだけに効き、投稿者による投稿削除は全掲載先に効く。

キーボードでは投稿先ボタン→検索→候補チェック→戻るの順に移動できるようにする。候補はチェックボックスのラベルに名前と発信元を含め、選択数・送信結果はスクリーンリーダーに通知する。狭い画面ではチップを折り返し、投稿ボタンを隠さない。日本語UI文言は `locales/ja-JP.yml` に追加し、ほかのlocale YAMLは編集しない。

### 下書きと予約投稿の範囲

ローカル下書きには「通常の投稿」の選択状態と投稿先 `{ origin, channelId }[]`、公開範囲、連合ON/OFF、確定待ちの作成キー・入力ハッシュを保持する。結果不明時は本人＋キーでreceiptを照会し、相手prepareの前に確定済み結果を回収する。サーバー下書きにも対応する情報を追加する。古い下書きのchannelIdはチャンネルだけの単一選択として復元する。Multi Noteの予約投稿は要件に含めず、新しい投稿先指定の予約確定は拒否する。既存の通常投稿・旧単一チャンネルの予約機能は互換性維持の対象とする。

## データとAPIの設計

### 正規の保存形

- `note` は本文・CW・添付・アンケート・返信/リアクションの対象を1件だけ持つ。新しい複数掲載の原本では `channelId = null` とする。
- 新規 `note_channel_placement` にnoteId、channelId、canonicalUri、sortAt、createdAt、掲載状態を置く。(noteId, channelId)と(channelId, canonicalUri)を一意にし、原本削除時はnoteIdをSET NULLにして最小の解除記録を残す。投稿と掲載は同じDBトランザクションで確定する。
- 相手原本の掲載は別の `gridspace_channel_placement` に自サーバーのチャンネルと原本URIを記録する案とする。相手の原本IDを自サーバーの `noteId` として保存・操作しない。本文は既存の権限付き取得を拡張して読み、チャンネル掲載のために通常共有のミラーを必須にしない。通常共有済みなら既存の同一URIの表現も使える。
- `note` に「通常の投稿」への配信を表すフラグを追加し、チャンネル掲載表から独立させる。段階1から「通常＋チャンネル」と「チャンネルのみ」を扱う。`channelId = null` だけを根拠に通常タイムラインや連合へ流さない。通常投稿先がない原本は既存チャンネル投稿と同じローカル限定の到達範囲にする。
- 既存の単一チャンネル投稿の `channelId` は互換性のため維持する。`includeDefault` のNULLは移行前の既存行に限り、全作成経路のサービスで新規行の true / false を確定する。旧APIの単一チャンネル投稿も初日から掲載表へ同時に書く。既存行はmigrationの外の再開可能なバッチで埋め、照合完了まで旧列と新表を併読する。解除済み行はバックフィルや旧列の参照で復活させない。マージ済migrationは編集せず、新規migrationで `up` と `down` を実装する。
- 複数掲載のレスポンスに `channelPlacements` を追加する。旧 `channelId` と `channel` は従来の単一チャンネル投稿だけで返す。旧クライアントが複数掲載を通常投稿と誤認し得るため、段階1の公開前に主要クライアントの表示・返信・引用を確認し、対応不能な操作はサーバーで拒否する。

### APIと配信処理

`notes/create` に任意の `channelIds` と「通常の投稿」選択状態を追加する。新しい指定方法では少なくとも1投稿先を必須にし、`channelId` との同時指定、重複、アーカイブ済み、閲覧条件の異なる組み合わせを拒否する。チャンネルがある場合は公開範囲 `public` を要求し、`home` / `followers` / `specified` を暗黙に `public` へ変更しない。「チャンネルのみ」は `localOnly=true`、通常投稿先もある場合は利用者が選んだ連合設定を維持する。旧 `channelId` だけのリクエストは従来どおり単一チャンネル専用として扱う。返信・引用・Renoteとの複数掲載は段階1では拒否する。作成リクエストには投稿者単位の冪等キーを持たせ、タイムアウト後の再試行で原本が増えないようにする。応答は原本1件と掲載先の確定結果を返す。

チャンネルタイムラインは掲載表から投稿を取り、旧 `note.channelId` の行も移行中に含める。通常タイムラインは新しい配信フラグを確認し、チャンネルだけの原本を除外する。同一サーバー内の段階1は既存の投稿ID順ページングを維持する。段階2の相手原本を含む新一覧は原本時刻＋canonical URIのカーソルへバージョンを分け、遅延確定は原本時刻の位置へ反映する。チャンネル別の投稿数・最終投稿日時・投稿者数・ランキングは有効掲載を基準に更新し、掲載解除時に再計算する。通常投稿と各チャンネルへのfanoutを独立して行い、同じ原本をホーム・通知へ複数回入れない。連合は通常投稿先・公開範囲・`localOnly`、ぐりすぺ通常共有は通常投稿先と既存共有条件で判定する。

新規原本は `channelId = null` なので、現行の `channelId IS NULL` 判定をそのまま残すとチャンネルだけの投稿が通常タイムラインへ混入し、`note.channelId` を比較するチャンネルのリアルタイム配信には出ない。DB取得・fanoutキャッシュ・WebSocketストリーム・SQL/Meilisearch検索を同じ投稿先判定へ切り替える。少なくともローカル/ホーム/ハイブリッド/グローバル/ユーザー一覧とチャンネル一覧、対応するストリームで通常＋チャンネル、チャンネルだけ、旧単一チャンネルを確認する。fanout有効・無効の両設定で1投稿IDの重複と漏れを検査する。詳細なファイル別の作業とテストは [multi-note-timeline.md](multi-note-timeline.md) を参照する。

共通の取得処理には通常タイムライン、ホーム、チャンネル、プロフィール、検索、推薦などの文脈を必須で渡し、指定なしを拒否する。通常投稿先の旧データ互換条件も共通処理に集める。`roles/notes`、`antennas/notes`、アンケート推薦、ぐりすぺ通常共有も段階1の対象に加える。アンケート推薦の `excludeChannels=true` は `poll.channelId` の複製値で判定せず、元ノートの通常投稿先を参照する。falseでは既存のチャンネル込み推薦の仕様を保つ。通常検索のチャンネル投稿の扱いは旧投稿との整合を確認してから確定する。

原本・掲載・冪等記録と後続処理のジョブ記録を同じDBトランザクションで保存し、fanout・集計・索引更新は再試行できる永続ジョブにする。再送やプロセス停止で通知・件数を二重加算しない。チャンネルごとのピン留めは有効掲載をサーバーで確認し、掲載解除時にはそのチャンネルのピンだけを外す。「削除して編集」は候補を復元し、新しい原本URI・作成キーで全投稿先を再認可する。旧URIの削除済み状態を解除しない。

複数掲載への返信は既存のローカル親行へのreplyIdを使い、親の掲載先を複製しない。通常投稿先を含む親には返信者側の通常ミラーを確保して通常返信を作り、専用の親には原本側でguest方式の会話内返信を作る。分散返信索引は追加しない。通常リアクションは行為者ホームの集合・revision同期、専用系は原本側集約を使う。通常の連合投票は既存経路、ペア内localOnlyと専用投票は署名付きの原本側処理へ振り分け、票数・本人選択も反映する。既存AP投票全体の排他再設計は後回しにする。通知・添付・削除の詳細は掲載契約案に従う。

検索、アンテナ、ユーザーノート、ミュート、Webhook、プラグインへのイベント、ノートメニュー、引用/Renote判定も旧 `channelId` だけに依存しないように監査する。掲載解除と原本削除は別の権限・別の操作として実装する。

返信の通常投稿先・ローカル限定の確定は `NoteCreateService` 内で親の状態から行い、旧クライアントやぐりすぺからの返信にも適用する。通常＋チャンネル原本を含むすべての引用・Renoteを拒否する案は取り下げ、通常投稿として連合した原本へのAnnounce・引用を受信できることを必須条件とする。チャンネル専用原本のローカル操作と掲載先の `allowRenoteToExternal` の扱いは書込開始前に確定する。

通常系は閲覧側の実在ミラーで表示・操作し、取込み前は返信・リアクションを無効にする。専用原本・会話内返信の標準API/SSR/公開リンク/添付は既存の公開条件で扱い、有効掲載が0件という理由だけで本人限定にはしない。進捗・再試行・削除の管理操作は投稿者だけに提供する。guest本人の削除は親や掲載の存続を要求しないdelete-reply、添付は用途別の書込許可を確認する既存ActionServiceの拡張で扱う。掲載解除による本文・添付の完全失効は今回の対象外。

### ActivityPub との境界

段階1では ActivityPub のオブジェクト形式、`Note` のフィールド、配送先の表現を拡張しない。通常の投稿先とチャンネルを同時に選び、連合ONなら、原本1件につき既存形式の `Create<Note>` アクティビティを1つ生成し、従来どおり対象の受信箱へ配送する。外部サーバーには通常投稿として届き、ローカルのチャンネル掲載情報は付けない。連合OFFなら配送しない。チャンネルだけの投稿は `localOnly=true` をサーバーで確定し、`Create` を配送しない。投稿後にチャンネル管理者が掲載だけを外しても ActivityPub の変更通知は送らない。原本を削除したときは、連合済みの原本につき既存形式の `Delete` アクティビティを1つ生成する。

この境界は `channelId = null` から推測しない。新しい通常投稿先フラグと `localOnly` の整合を `notes/create` と `NoteCreateService` で保証する。`ActivityPubServerService` の公開ノートURL・activity URL・outboxで、チャンネルだけの原本が取得できず、通常＋チャンネルの原本は1件として取得できることを検証する。`NoteDeleteService` の配送条件も確認する。既存の `ApRendererService` と ActivityPub の JSON は、これらの検証で変更が必要と判明しない限り触らない。

## 実装順と受け入れ条件

1. **保存と読み取り**: 新規migration、モデル、共通判定、掲載の作成・解除、旧行の段階移行を用意する。全作成経路でフラグを確定し、旧APIにも掲載表を同時に書く。旧単一チャンネル投稿の表示・返信が変わらないことをDBテストで確認する。
2. **同一サーバーの投稿API**: 複数掲載を原子的に作成し、再試行で原本が増えないようにする。無効な投稿先は全体を作成前に拒否する。
3. **タイムラインと会話**: DB取得・fanout有効/無効・リアルタイム配信・推薦・ぐりすぺ通常共有の各経路で共通判定を適用する。各チャンネルと選択した通常タイムラインに同じ投稿IDが1件出る。チャンネルだけの投稿は通常タイムラインと通常共有へ出ず、推薦は除外指定を守る。返信・リアクション・アンケートは同じ原本を指す。掲載解除でそのチャンネルからだけ消え、永続ジョブ再試行で件数・通知が増えない。
4. **Web UI**: 投稿先シートと投稿詳細を実装する。通常投稿、単一チャンネル投稿、通常＋チャンネル、チャンネルのみ、投稿先0件の防止、公開範囲の衝突、選択不可、送信中、失敗、狭い画面をStorybookとE2Eで確認する。下書きの保存・復元も確認する。
5. **連携先**: ぐりすぺ側の署名付き掲載プロトコルと状態照会を実装し、片側障害・失効・再試行・削除伝播を2サーバーのテストで確認する。
6. **公開判定**: API互換、公開範囲、モデレーション、既存クライアントと必須M1〜M8を検証する。通常＋チャンネルは原本ごとにCreateを1つ生成し、専用原本は通常TL/RSS/共有/AP自動配送へ出さない。一方、原本のWeb公開URL・会話・添付は既存の公開条件で開けることを確認する。連合済み原本の削除はDeleteを1つ生成する。両サーバーの対応まで連携先候補は選択不可とする。

配備はschema追加、全サーバー・ワーカーへの互換実装の配備、バックフィルと検索再索引、取得経路の照合、新規書込の有効化の順とする。書込開始後は対応前の旧版サーバー・ワーカーへ戻してはいけない。機能停止時も新旧両形式を読むコード、掲載表、ジョブを残す。書込を止めるフラグと切り戻し禁止条件を運用手順へ記録する。

実装変更時は近接テスト、変更ファイルのESLint、SPDX、locale安全性を確認する。APIスキーマ変更時は `pnpm build-misskey-js-with-types`、entity・migration変更時は `pnpm --filter backend check-migrations` を実行する。共通取得の文脈指定を型・実行時に検査し、通常投稿の判定を単一 `channelId` に戻す変更をCIで検出する。migrationの `down` は新機能の投稿データが存在しない場合だけを対象にする。

## 実装前に確定する判断

1. 対象を「公開チャンネル、通常投稿先との同時掲載、チャンネルのみの掲載」とする。公開センシティブチャンネルもセンシティブ属性だけで除外しない。必要なCWは投稿者が設定し、チャンネル数に固定上限を置かない。
2. 新しいチャンネル専用への返信は共通会話の詳細に集め、各チャンネル一覧には独立した返信行を出さない。通常投稿先ありの親には既存の通常返信を使う。
3. 連携先チャンネルだけの投稿は通常配信せず、段階2で既存の公開条件を確認する専用取得を使う。本文閲覧に掲載の存続を必須化しない。
4. チャンネル管理者は掲載だけを解除し、原本・他チャンネルの掲載は保持する。全掲載先消失時も原本URLと会話は既存の公開条件で残り、最小の削除・解除記録は期限なしで保持する。
5. 通常検索とチャンネル込み推薦の旧投稿との整合、通常＋チャンネルのRenoteと `allowRenoteToExternal`、旧チャンネルと新チャンネル専用投稿の公開範囲変更条件は新規書込前に確定する。

これらは本計画の提案であり、実装開始前にUIの試作と2サーバーの契約テストで妥当性を確認する。
